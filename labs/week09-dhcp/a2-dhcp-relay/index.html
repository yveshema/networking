DHCP Relay

Time: 40 min

Needs: one OL9 Router node (R1), one Ethernet Switch (SW2), one VPCS node added to the existing w09-a1-dhcp project

GNS3 project: w09-a1-dhcp (reuse it)

Info

Times listed are approximate and provided as timing guidelines only. Take as much time as you need to complete the activity.

Topology

  • Delete the additional VPCS clients you added in the last step, leaving only the server, PC1 and PC2
  • Cable R1.eth0 to SW1 and R1.eth1 to SW2.
  • Cable PC3 to SW2 as well

There are two networks in this topology:

  • LAN1: 192.168.10.0/28(R1, DHCP-SRV, PC1, PC2)
  • LAN2: 172.16.10.0/28 (R1, PC3)

Do this - configure the router

Start R1, login as root, configure its addresses and enable IP forwarding:

echo "net.ipv4.ip_forward = 1" | tee -a /etc/sysctl.d/99-ip-forwarding.conf > /dev/null
sysctl --system

nmcli con add type ethernet ifname eth0 con-name eth0
nmcli con add type ethernet ifname eth1 con-name eth1

nmcli con mod eth0 ipv4.method manual ipv4.addresses 192.168.10.1/28
nmcli con mod eth1 ipv4.method manual ipv4.addresses 172.16.10.1/28

for i in eth0 eth1; do
    nmcli con up $i
done

Update DHCP-SRV server configuration. Replace the existing configuration with the following:

{
  "Dhcp4": {
    "interfaces-config": { 
        "interfaces": [ "eth0" ] 
    },
    "lease-database": { 
        "type": "memfile", 
        "name": "/var/lib/kea/kea-leases4.csv" 
    },
    "valid-lifetime": 600,
    "subnet4": [
      {
        "id": 1,
        "comment": "LAN 1",
        "subnet": "192.168.10.0/28",
        "pools": [ { "pool": "192.168.10.2 - 192.168.10.6" } ],
        "option-data": [ 
            { "name": "routers", "data": "192.168.10.1" } 
        ]
      },
      {
        "id": 2,
        "comment": "LAN 2",
        "subnet": "172.16.10.0/28",
        "pools": [ { "pool": "172.16.10.2 - 172.16.10.6" } ],
        "option-data": [
            { "name": "routers", "data": "172.16.10.1" }
        ]
      }
    ]
  }
}

Validate the configuration, then restart the server:

kea-dhcp4 -t /etc/kea/kea-dhcp4.conf

systemctl restart kea-dhcp4

What just happened

  • We made DHCP-SRV responsible for two distinct subnets by just adding another object to the subnet4 list
  • option-data can hold additional optional settings, including in this case the address of the router on each segment. The server uses this information to tell the clients where their default gateway is located.

The server is now equipped to serve two subnets, but one subnet is behind a router, which presents a problem. DISCOVER packets are broadcast, and the router does not forward broadcast packets.

So, at this point, requests from LAN2 cannot reach the server. We need a DHCP relay.

Do this - configure the relay

On R1: 

dhcrelay -d -4 -id eth1 -iu eth0 192.168.10.14

  • -id: Downstream interface, i.e., the interface facing the clients
  • -iu: Upstream interface, i.e., the interface facing the server
  • 192.168.10.14: the address of the server
  • the -d option lets the process run in the foreground. -4 selects IPv4 address family

Start PC2, then:

ip dhcp

ping 192.168.10.2 -c 1

In Wireshark, expand the DISCOVER DHCP packet and locate the Relay agent IP address field. It contains R1 downstream (eth1) IP address. The server uses this to decide which subnet to assign addresses from.

Currently, dhcrelay is running in the foreground and will not survive a reboot. We fix this in the next section.

Do this - run the relay as a service

Run the following on R1:

systemctl cat dhcrelay

This will show dhcrelay service definition, which looks like this:

# /usr/lib/systemd/system/dhcrelay.service
[Unit]
Description=DHCP Relay Agent Daemon
Documentation=man:dhcrelay(8)
Wants=network-online.target
After=network-online.target

[Service]
Type=notify
ExecStart=/usr/sbin/dhcrelay -d --no-pid
StandardError=null

[Install]
WantedBy=multi-user.target

The key line is the one starting with ExecStart. It specifies the command to launch the service. The problem is that it has no way of knowing beforehand where the server is located or which interfaces are downstream or upstream. So, we need to edit the definition.

On R1: 

systemctl edit dhcrelay

Add the following lines in the space between comments:

[Service]
ExecStart=
ExecStart=/usr/sbin/dhcrelay -d -4 -id eth1 -iu eth0 192.168.10.14

We use systemctl edit to override parts of the existing definition, specifically the ExecStart directive. We first clear the existing command by assigning an empty string to ExecStart, after which we can now specify our own custom command.

Enable and start the service:

systemctl enable --now dhcrelay

systemctl is-active dhcrelay

On PC3, refresh the lease and ensure DHCP still succeeds:

ip dhcp
