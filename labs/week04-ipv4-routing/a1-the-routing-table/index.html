W4·A1 — The routing table

Time: 40 min · Needs: one OL9 Router, one OL9 PC, one Ethernet switch · GNS3 project: w04-a1-routing-table

The question: a host has one cable and can reach the entire internet through it. What does it consult to decide where to send each packet, and how does it choose when more than one entry fits?

Build it

  LAN1 192.168.100.0/24      10.0.0.0/30

  PC1 ─── SW1 ─── R1 ───────────
  .10             .1  10.0.0.1

R1 is an OL9 Router, PC1 an OL9 PC, and SW1 a plain Ethernet switch — the LAN needs one, even with a single host on it. Nothing is cabled to R1:eth1; the subnet on it exists purely to be somewhere PC1 is not attached.

An OL9 Router has four network adapters, and NetworkManager will take over any you leave alone — which undoes your addressing a moment after you type it. So tell it to leave all four alone, even though this activity only uses two.

# on R1
for i in eth0 eth1 eth2 eth3; do nmcli device set $i managed no; done
ip addr add 192.168.100.1/24 dev eth0 ; ip link set eth0 up
ip addr add 10.0.0.1/30      dev eth1 ; ip link set eth1 up
sysctl -w net.ipv4.ip_forward=1

# on PC1
nmcli device set eth0 managed no
ip addr add 192.168.100.10/24 dev eth0 ; ip link set eth0 up

Predict first

PC1 has one address and no routes you have typed.

  1. How many entries are in its routing table? _
  2. Can it reach 192.168.100.50? ☐ yes ☐ no
  3. Can it reach 10.0.0.1, which is on the router it is plugged into? ☐ yes ☐ no

Do this — the table you did not write

# on PC1
ip route show
ping -c1 192.168.100.1
ping -c1 10.0.0.1

What just happened

  • There is one entry, and you never typed it: 192.168.100.0/24 dev eth0 proto kernel scope link. Assigning an address to an interface is an implicit claim that its whole subnet is reachable out that port, and the kernel records that claim as a route. proto kernel means exactly "I did this, you did not".
  • 192.168.100.1 worked — it matches the connected route, so PC1 sends it directly, ARPing for the destination itself.
  • 10.0.0.1 failed, with Network is unreachable, and note where the error came from: PC1's own kernel, instantly, before anything was transmitted. Confirm with a capture — the wire is silent. A host with no matching route does not try and fail; it does not try.
  • 10.0.0.1 is on the router PC1 sends everything through, two cables away. Physical connectivity is irrelevant. The table is the whole of the decision.

Do this — a default route

# on PC1
ip route add default via 192.168.100.1
ip route show
ping -c1 10.0.0.1

What just happened

  • One line, and every destination in the world is now attempted. default is 0.0.0.0/0 — a prefix of length zero, which matches everything, and is therefore the entry of last resort.
  • This is what "default gateway" means, and it is the entry your laptop gets from DHCP.
  • It says nothing about whether the destination exists. It says where to send things you have no better idea about. Every failure from here on is somewhere else's problem, which is why diagnosing them needs A2's technique.

Do this — interrogate the decision

Add more specific routes and ask the kernel which one it would use. First, though, give R1 two extra addresses on the interface PC1 is plugged into:

# on R1
ip addr add 192.168.100.2/24 dev eth0
ip addr add 192.168.100.3/24 dev eth0
ip addr show eth0

An aside — one interface, several addresses. An interface is not limited to one address. eth0 now answers to .1, .2 and .3 at once: same cable, same MAC, same subnet, and R1 replies to ARP for all three. Older documentation calls these aliases and names them eth0:0, eth0:1; the ip command simply lists them for what they are, a set of addresses on one interface. Real uses:

  • one server hosting several services that each need their own address rather than sharing one
  • renumbering — a router holds the old and the new gateway address simultaneously, so hosts move across a few at a time instead of all at the instant of the change
  • a management address kept apart from the service address, so the box stays reachable when the service address moves elsewhere

W4·A5 gives one router several addresses a different way: separate VLAN subinterfaces, one address each. Several addresses on one interface, or several interfaces on one port — both are common, and they are not the same mechanism.

Here they do something more specific: with three addresses on R1, three routes can each point at a different one. What that buys you is the point of what follows.

# on PC1
ip route get 192.168.100.50
ip route get 10.0.0.1
ip route get 8.8.8.8

ip route add 10.0.0.0/24 via 192.168.100.2
ip route get 10.0.0.1

ip route add 10.0.0.0/30 via 192.168.100.3
ip route get 10.0.0.1

ip route get 10.0.0.9
ip route show match 10.0.0.1
ip route show

What just happened

  • ip route get is the routing table's own answer, not your reading of it — use it instead of arguing about which line applies. Read carefully what it reports: the decision, as a next hop, an outgoing interface and a source address. It does not report which entry produced that decision.
  • That distinction is why R1 needed three addresses. Had all three routes pointed via 192.168.100.1, all three answers would have come back exactly the same and you could not tell which route produced them — the packets reach the same box either way. Giving each route its own next hop is what makes the choice visible, and it costs nothing, since .1, .2 and .3 are all R1.
  • Three destinations, three answers, one table: 10.0.0.1 → via .3, the /30. 10.0.0.9 → via .2, the /24, since it is outside the /30. 8.8.8.8 → via .1, the default. Longest prefix wins, always, regardless of the order lines appear in or the order you added them.
  • The rule has a good reason: a longer prefix is a more specific claim, and the most specific applicable claim is the one most likely to be correct. It is how a global routing table can hold a broad statement and a narrow exception at once, with no conflict.
  • ip route show match 10.0.0.1 asks the other half of the question: not which route wins but which routes could have won. It lists all three. Note that it does not put them in order of preference — the order is the table's own. route get names the winner; show match names the list the winner was chosen from.

Do this — take the default away

# on PC1
ip route del default
ip route del 10.0.0.0/24
ip route del 10.0.0.0/30
ip route show

ping -c1 192.168.100.1
ping -c1 10.0.0.1

Sort the two results into "still works" and "does not".

What just happened

  • Direct delivery survives; everything else does not. The connected route is the only thing a host truly needs and the only thing it gets for free.
  • Those are the two cases a host distinguishes, every time it sends anything: is the destination inside a prefix I am attached to? If yes, ARP for it and send. If no, ARP for a gateway and send it there instead, with the destination IP untouched.
  • Week 1's /25 break (W1·A1) was this decision going wrong. PC1 classified PC2 as "not local" and had no gateway to fall back on. You now have the vocabulary for what you saw in week 1.
