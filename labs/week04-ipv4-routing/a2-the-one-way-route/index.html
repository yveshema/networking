W4·A2 — The one-way route ★

Time: 50 min · Needs: two OL9 Routers, two OL9 PCs, two Ethernet switches, Wireshark · GNS3 project: w04-base — keep this project; A3 and A4 continue in it

The question: every interface is up, every address is correct, every subnet is right, and the ping fails. Find out why without guessing.

Build it

  LAN1 192.168.100.0/24      transit 10.0.0.0/30      LAN2 192.168.200.0/24

  PC1 ─── SW1 ─── R1 ═══════════════════════════ R2 ─── SW2 ─── PC2
  .10             .1  10.0.0.1         10.0.0.2  .1             .10

R1 and R2 are OL9 Routers, PC1 and PC2 OL9 PCs, SW1 and SW2 plain Ethernet switches. Each LAN gets a switch even though only one host sits on it — that is what a LAN is, and A6 and A8 will both plug something else into SW1.

Tell NetworkManager to leave every interface alone before you address anything, or it will undo your work a moment after you type it. A router has four adapters, so that means all four, even though this topology only uses two:

# on R1 and on R2
for i in eth0 eth1 eth2 eth3; do nmcli device set $i managed no; done

# on PC1 and on PC2
nmcli device set eth0 managed no

# R1
ip addr add 192.168.100.1/24 dev eth0 ; ip link set eth0 up
ip addr add 10.0.0.1/30      dev eth1 ; ip link set eth1 up
sysctl -w net.ipv4.ip_forward=1

# R2
ip addr add 192.168.200.1/24 dev eth0 ; ip link set eth0 up
ip addr add 10.0.0.2/30      dev eth1 ; ip link set eth1 up
sysctl -w net.ipv4.ip_forward=1

# PC1
ip addr add 192.168.100.10/24 dev eth0 ; ip link set eth0 up
ip route add default via 192.168.100.1

# PC2
ip addr add 192.168.200.10/24 dev eth0 ; ip link set eth0 up
ip route add default via 192.168.200.1

Check the transit link works before going further: from R1, ping -c1 10.0.0.2.

Predict first

R1 knows about 192.168.100.0/24 and 10.0.0.0/30. R2 knows about 192.168.200.0/24 and 10.0.0.0/30. Neither has been told about the other's LAN.

  1. PC1 pings PC2. Where does the packet get to before it stops? _
  2. What error will PC1 report? _

Part 1 — Add one route, not two

Deliberately configure only the forward direction:

# on R1 only
ip route add 192.168.200.0/24 via 10.0.0.2
ip route show

Add nothing to R2. Then from PC1:

ping -c2 192.168.200.10

What just happened

  • No replies, and ping gives you nothing to work with — no error, just silence and 100% loss. The most useless failure mode there is.
  • Every check you can make from PC1 passes. Its address is right, its gateway responds, its route is correct, the cable is up. The fault is not visible from either endpoint, and this is the situation that makes people start changing things at random.

Part 2 — Diagnose it properly

Do not guess. Capture at two places at once: the PC1↔R1 link and the R2↔PC2 link. Then ping again.

Fill this in from the captures:

Link Echo request seen? Echo reply seen?
PC1 ↔ R1
R2 ↔ PC2

What just happened

  • The request appears on both links. It crossed both routers and was delivered to PC2. The forward path is perfect.
  • PC2's capture shows it generating a reply — and the reply never reaches PC1.
  • On R2, ask the kernel directly:
# on R2
ip route get 192.168.100.10

Network is unreachable. R2 received a perfectly good packet, answered it, and had nowhere to send the answer.

  • A route describes one direction only. R1 was told how to reach LAN2. Nothing told R2 how to reach LAN1, and nothing ever would — routers do not learn return paths from traffic the way a switch learns MAC addresses. This is the single most important difference between what week 3's switch did and what a router does.
  • Notice how thoroughly the endpoints were unable to see this. PC1 saw silence. PC2 saw a normal request and answered it, entirely satisfied. Only two simultaneous observations located the fault, and the location was a third device that reported nothing.

Part 3 — Fix it

# on R2
ip route add 192.168.100.0/24 via 10.0.0.1
ip route show

From PC1: ping -c2 192.168.200.10.

What just happened

  • It works, immediately, with no other change. Two routes for one conversation — one per direction, on different devices.
  • Count what a two-router path required: two static routes, and neither router can be checked in isolation. Now imagine ten routers, where every pair needs this and every new subnet touches every device. That arithmetic is the entire argument for dynamic routing protocols, and it is why the course arrives at OSPF later.

Part 4 — The same fault, disguised

Remove R2's route and instead add a wrong one:

# on R2
ip route del 192.168.100.0/24
ip route add 192.168.100.0/24 via 10.0.0.2      # its own address
ip route get 192.168.100.10

Ping again from PC1, and check the transit-link capture.

What just happened

  • The route was accepted, and nothing warned you. ip route get answers confidently — but read its answer closely, because there is no via in it:
192.168.100.10 dev eth1 src 10.0.0.2
  • A next hop that is one of the router's own addresses is not a next hop. The kernel discards it and treats the whole /24 as directly attached to eth1 — the transit link. So R2 does not forward these packets anywhere. It tries to deliver them on the transit link itself.
  • The capture shows exactly that: R2 ARPing for 192.168.100.10 on the transit wire, and getting no answer, because PC1 is on the far side of R1 and was never on this cable.
  • R2 also sends R1 an ICMP redirect — "to reach 192.168.100.10, send to 192.168.100.10" — because it is sending the packet back out the interface it came in on. When the ARP finally fails, it sends host unreachable. A6 explains that channel properly. For now note only that both messages came from R2 and describe R2's decision, not the destination.
  • Compare with Part 1: a missing route fails loudly at the kernel and silently at the endpoint. A wrong route is accepted everywhere, answers ip route get confidently, and then fails somewhere else entirely, in a way that points at the wrong device. "There is a route" is not the same as "the route is right", and the only proof is end-to-end traffic.
  • Put the correct route back before continuing to A3.
