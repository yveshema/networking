W4·A7 — Echo, and what ping does not prove

Time: 45 min · Needs: A6 finished and restored · GNS3 project: w04-base (continue)

The question: A6 was about ICMP reporting failures. Ping is the opposite — a query, and the least representative thing in the protocol. It is also the tool you will trust most and should trust least.

Predict first

  1. Two pings to the same host, running at once. How does each one recognise its own replies?
  1. What is inside a ping's payload, and who chose it? _
  2. A router cannot forward a packet that is too large, and you have forbidden fragmentation. What comes back? _

What just happened

  • Echo request is type 8, echo reply is type 0. Both use code 0 — the code field carries no information here at all.
  • The four type-dependent bytes from A6 are used here as Identifier and Sequence.
  • ICMP has no ports. With two pings running, replies arrive at one host and must be sorted out somehow — so ICMP invented a demultiplexing field of its own. That is exactly what a port is, reinvented, in a protocol that lacks them. When you meet ports properly at the transport layer, this is the problem they solve.
  • Sequence numbers are what make loss and reordering visible. Ping's summary line is arithmetic over those numbers, nothing more.

Do this — the payload is yours

# on PC1
ping -c1 -s 32 -p 48656c6c6f20323632300a 192.168.200.10

In another terminal on PC1, before running it:

tcpdump -i eth0 -X -c2 icmp

What do you see in the payload of the reply? _

What just happened

  • The payload is arbitrary, chosen by the sender, and returned verbatim. RFC 792 requires only that it come back unchanged; it says nothing about what it may contain.
  • The default payload is not empty — it holds a timestamp, and that is how ping computes round-trip time. The sender does that arithmetic. The network contributes nothing to the measurement and no device on the path is aware it is being timed.
  • Arbitrary content, echoed reliably, in a protocol firewalls habitually permit, is a data channel. Tools exist that tunnel entire login sessions through ping payloads. "We allow ICMP" is a statement about a protocol number — it says nothing whatever about what crosses the boundary.

Do this — the message that is really a mechanism

# on PC1
ping -c1 -M do -s 1472 192.168.200.10      # fits exactly
ping -c1 -M do -s 1473 192.168.200.10      # one byte too many

Now shrink the transit link and sweep again:

# on R1
ip link set dev eth1 mtu 1400

# on PC1
ping -c1 -M do -s 1472 192.168.200.10
ping -c1 -M do -s 1372 192.168.200.10
ip route get 192.168.200.10

What just happened

  • Type 3, Code 4 — fragmentation needed and DF set. It is filed under "destination unreachable", but nothing is unreachable and nothing has failed. This is the mechanism of path MTU discovery.
  • Here the four type-dependent bytes carry the next-hop MTU. The router does not merely refuse — it tells you the number to use. That field was reserved in the original specification and put to work later.
  • PC1 cached it per destination, which you can see in ip route get. Everything it sends that way from now on will fit.
  • This only works because of A6. The error quotes your original packet, so PC1 knew which destination to shrink for. Without those quoted bytes the message would be useless.

Do this — break it, and see why blocking ICMP is expensive

# on R1
nft add table inet f
nft add chain inet f out '{ type filter hook output priority 0; policy accept; }'
nft add rule inet f out icmp type destination-unreachable drop

# on PC2
python3 -m http.server 8080 &

# on PC1
curl -o /dev/null -m 20 http://192.168.200.10:8080/
ping -c1 192.168.200.10

Clean up: nft flush ruleset on R1, ip link set dev eth1 mtu 1500.

What just happened

  • Small packets pass. Large ones vanish. The sender is never told why, so it retransmits the same oversized packet forever.
  • This is a path MTU black hole, and it is one of the hardest faults in networking to diagnose: connections establish (the handshake is small), then hang the moment real data flows. Ping works. Traceroute works. Everything "looks fine".
  • "Block ICMP, it's a security risk" is common advice and this is what it produces. The protocol you filtered was the one that would have told you.

Do this — what ping actually proves

# a host that answers ping and serves nothing
# on R1
systemctl stop sshd
# on PC1
ping -c1 192.168.100.1
ssh 192.168.100.1

# a host that ignores ping and works perfectly
# on PC2
nft add table inet f
nft add chain inet f in '{ type filter hook input priority 0; policy accept; }'
nft add rule inet f in icmp type echo-request drop
# on PC1
ping -c2 -W2 192.168.200.10
curl -m5 -o /dev/null -w '%{http_code}\n' http://192.168.200.10:8080/

Clean up: nft flush ruleset on PC2, systemctl start sshd on R1.

What just happened

  • Reachable is not usable. R1 answered every ping while providing nothing you wanted.
  • Silent is not down. PC2 ignored every ping while serving pages perfectly.
  • So both conclusions people routinely draw from ping — "it pings, so it's fine" and "it doesn't ping, so it's down" — are unreliable, and they fail in opposite directions.
  • Put beside A4's caveats about traceroute, you now have a calibrated view of the two tools you will otherwise over-trust for the rest of your career. Neither is wrong. Both answer a narrower question than the one you meant to ask.
