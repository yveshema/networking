W4·A9 — Forge the packet

Time: 50 min · Needs: A6 and A7 finished · GNS3 project: w04-a9-forge (a fresh three-node project — see Topology) · Extension activity

The question: In A6 and A7 you read ICMP. Now build it. When you can assemble a packet field by field, two things become obvious that no capture can show you: exactly which fields the protocol fixes and which it leaves to you, and that nothing checks whether you are telling the truth.

Predict first

  1. Can you send an echo reply that nobody requested? _
  2. If you set the ICMP type to a number IANA never assigned, what happens? _
  3. Can you make one host believe a third host's network path is tiny — without being either of them? _

Topology

                10.10.0.0/24

   ATTACK       TARGET       VICTIM (for the last part)
    .10          .20           .30
      └────────────┼────────────┘
                  SW1

Three OL9 PCs on one Ethernet switch — one broadcast domain, which is what lets a forged reply reach a host that never asked for it.

Run scapy as root (sudo scapy). Capture on TARGET's link throughout.

Do this — build echo from nothing

# on ATTACK, in scapy
p = IP(dst="10.10.0.20")/ICMP()/b"built by hand"
sr1(p, timeout=2)
Default ICMP type scapy chose
Did a reply come back? ☐ yes ☐ no
Type of the reply

What just happened

  • Three lines built a complete, valid echo request — IP() for the network layer, ICMP() for the message, a payload of your choosing — and a real host answered it. You have now constructed the protocol you spent two activities observing.
  • ICMP() defaulted to type 8. Change it explicitly and watch the taxonomy hold:
sr1(IP(dst="10.10.0.20")/ICMP(type=8), timeout=2)     # echo — answered
sr1(IP(dst="10.10.0.20")/ICMP(type=99), timeout=2)    # unassigned — silence
  • Type 8 is answered. Type 99 is discarded without a word. The type field is a fixed vocabulary; invent a word and no one understands it. The payload, by contrast, was whatever you typed. Fixed taxonomy, free payload — exactly the split A7 named.

Do this — the reply nobody asked for

# on ATTACK
send(IP(dst="10.10.0.20")/ICMP(type=0, id=0x1234, seq=1)/b"unsolicited")

Watch TARGET in the capture.

What just happened

  • You sent an echo reply (type 0) that answered no request. TARGET received it and did nothing — it had no outstanding ping with that identifier, so the reply matched nothing and was dropped.
  • Harmless here, but note the shape of it: ICMP messages carry no proof of who sent them or that they were solicited. The receiver's only defence is "did I ask for this?" — and for error messages, as the next part shows, even that check is weak.

Do this — forge an error, and change a stranger's connection

This is the capstone. Recall A7: a fragmentation needed error (type 3, code 4) carries a next-hop MTU, and the receiver caches it per destination. That message is unauthenticated. So you can send it yourself.

# on ATTACK — tell TARGET that reaching VICTIM requires tiny packets.
# The quoted inner packet must look like traffic TARGET sent to VICTIM.
inner = IP(src="10.10.0.20", dst="10.10.0.30")/TCP(sport=12345, dport=80)
forged = IP(dst="10.10.0.20")/ICMP(type=3, code=4, nexthopmtu=296)/inner
send(forged)

# on TARGET
ip route get 10.10.0.30
MTU TARGET now caches for VICTIM
Were you either TARGET or VICTIM? ☐ no

What just happened

  • TARGET believed a complete stranger's claim about a path it is not on, and shrank its packets to VICTIM accordingly. You never touched VICTIM.
  • It worked because the forged error quoted a plausible inner packet — the source, destination and ports of traffic TARGET might really have sent. That quoted header, from A6, is how a host decides an error is "about" one of its connections. Here it is the whole attack surface: guess the four-tuple, and the error is accepted.
  • This is why real stacks now sanity-check the quoted bytes — does this connection exist, is that sequence number in a window I actually sent — before acting on an ICMP error. A6's structural detail and A7's PMTU mechanism were the two halves of a live security problem, and you just assembled it.

Restore: ip route flush cache on TARGET.

Do this — options ping cannot make

# on ATTACK — an IP option set by hand, and a deliberately wrong checksum
send(IP(dst="10.10.0.20", options=[IPOption_RR(length=39, pointer=4)])/ICMP())
send(IP(dst="10.10.0.20", chksum=0xdead)/ICMP()/b"bad checksum")

What just happened

  • You built a Record Route option directly, choosing its size — something ping -R fixes for you. Compare its handling to A8: the lab honours it, and a real path would not.
  • The bad-checksum packet was silently discarded by TARGET's IP layer. No error, no reply — a corrupt header has no trustworthy return address to complain to, so the only safe action is to drop it. That is why a checksum failure is invisible from the sending side.
