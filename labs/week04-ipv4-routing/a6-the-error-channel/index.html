W4·A6 — The error channel

Time: 45 min · Needs: A2's topology, working · GNS3 project: w04-base (continue)

The question: Every failure so far has looked identical from the keyboard — "it doesn't work". The network has in fact been telling you exactly what went wrong and which device decided so. This is how to read it.

Predict first

  1. ping 203.0.113.1 from PC1, which has no route to it. How many packets leave PC1? _
  2. A UDP datagram to a port nothing is listening on. What comes back, and from whom? _
  3. A host that is switched off. Who reports "host unreachable" — the missing host, or something else? _

Do this — five failures, five origins

Start a capture on the PC1↔R1 link and leave it running for all five.

# 1 — no route on your own machine
# on PC1
ip route show
ping -c1 203.0.113.1

# 2 — no route on a router
# on PC1
ping -c1 198.51.100.7

# 3 — route exists, host absent
# on PC1
ping -c1 -W5 192.168.200.99

# 4 — host present, nothing listening
# on PC1
echo hello | ncat -u -w1 192.168.200.10 9999

# 5 — a device that refuses on purpose
# on R2
nft add table inet filter
nft add chain inet filter forward '{ type filter hook forward priority 0; policy accept; }'
nft add rule inet filter forward ip daddr 192.168.200.10 icmp type echo-request \
    reject with icmp type admin-prohibited
# on PC1
ping -c1 192.168.200.10

Now change case 5 from reject with icmp type admin-prohibited to drop and repeat:

# on R2
nft flush ruleset
nft add table inet filter
nft add chain inet filter forward '{ type filter hook forward priority 0; policy accept; }'
nft add rule inet filter forward ip daddr 192.168.200.10 icmp type echo-request drop
# on PC1
ping -c1 192.168.200.10

What came back this time? _

Clean up before continuing: nft flush ruleset on R2.

What just happened

  • Case 1 put nothing on the wire at all. Check the capture — it is empty. PC1's kernel looked in its routing table, found nothing, and refused before transmitting. "Network is unreachable" here is a local error message, not an ICMP packet, and no device on the network ever learned you tried. Distinguishing a local refusal from a network report is the first split in any diagnosis, and A1 is where you learned why the lookup happens first.
  • Case 2 came from R1 — Type 3, Code 0, net unreachable. R1 was the first device that had to make a forwarding decision it could not make, so R1 is the one that complained.
  • Case 3 came from R2, not from the absent host — obviously, since nothing is there to answer. R2 has 192.168.200.0/24 directly connected, so it ARPed for .99, got no reply, and only then reported Type 3 Code 1. That is why it took seconds rather than milliseconds. The device that reports an error is the device that discovered it.
  • Case 4 came from PC2 itself — Type 3 Code 3, port unreachable. Note what just happened: a network-layer protocol reported a transport-layer fact. ICMP has no ports of its own, yet this message identified one. Part 2 explains how.
  • Case 5, reject vs drop. Both stopped the traffic. Only one told you. Silence is a configuration decision someone made, not an absence of information — and from PC1 it is indistinguishable from a cable being unplugged.

Do this — what is inside an ICMP error

Pick any of the Type 3 messages in Wireshark and expand it fully.
Bytes of your original packet quoted back
Can you see the destination port you sent to? ☐ yes ☐ no

What just happened

  • Every ICMP error carries the original IP header plus the first 8 bytes of the datagram that caused it. Not a description of your packet — your packet.
  • For TCP and UDP, those 8 bytes are exactly the source and destination ports. So the host receiving the error can attribute it to one specific socket instead of "something, somewhere, failed".
  • That is how case 4 could name a port: it quoted your datagram back at you.
  • This is the mechanism the entire protocol rests on. A7's path MTU discovery is impossible without it, and A9's forged errors are dangerous because of it.

Do this — where ICMP actually sits

# on PC1
ping -c1 192.168.200.10 &
tcpdump -i eth0 -v -n icmp -c1

Read the IP header in that output, not the ICMP part.
IP protocol number carrying ICMP
Protocol number for TCP / for UDP

What just happened

  • ICMP travels inside IP, in the same slot TCP (6) and UDP (17) occupy. Protocol 1. There is no extra layer and no shim.
  • Yet RFC 792 calls ICMP "an integral part of IP", required in every implementation. It is encapsulated like a guest and behaves like the host — a protocol whose job is to let the network layer talk about itself.
  • Here is the evidence. A TCP or UDP checksum includes a pseudo-header built from the IP addresses, because those are separate protocols that need to verify they were delivered to the right place. The ICMPv4 checksum covers only the ICMP message. It does not check, because it is not a guest.
  • The ICMP header is 8 bytes: type, code, checksum, then four bytes whose meaning depends entirely on the type. In an error they are unused; you will meet two more uses in A7.

Do this — an ICMP message when nothing is wrong

Cable a second link, R2:eth2 to SW1, and address it.

Notice what that does to the topology: R1 and R2 are now both on LAN1. Everywhere else in this week a router-to-router link is a point-to-point cable with nothing else on it. Here two routers deliberately share one broadcast domain, because that is the only arrangement in which the message you are about to see can arise at all.

# on R2
ip addr add 192.168.100.2/24 dev eth2
ip link set eth2 up

# on R1 — point the route to LAN2 at R2's LAN1 address
ip route replace 192.168.200.0/24 via 192.168.100.2
sysctl -w net.ipv4.conf.all.send_redirects=1

# on PC1
sysctl -w net.ipv4.conf.all.accept_redirects=1
ping -c2 192.168.200.10
ip route get 192.168.200.10
Did the ping succeed? ☐ yes ☐ no
ICMP type seen on the capture

What just happened

  • The ping worked. R1 forwarded it correctly, exactly as asked. And R1 also sent PC1 an ICMP message.
  • Type 5, Redirect. It is not an error and nothing failed. It is advice: "for that destination, R2 is a better first hop than me — you are both on my segment, so stop sending it through me." Here the four type-dependent bytes carry the address of the better gateway.
  • PC1 believed it. ip route get now names 192.168.100.2, from a route PC1 was never configured with and no administrator typed.
  • So ICMP is not the failure channel. It is IP's control channel, and errors are merely its most visible use. The other everyday query is timestamp request/reply (types 13 and 14), which asks a host for its clock — no fault involved.
  • In IPv6 the healthy case dominates completely: neighbour discovery, the replacement for ARP, is ICMPv6. A perfectly working IPv6 network emits ICMP continuously and would not function without it. You will see that directly in the IPv6 project.

Restore before A7:

# on R1
ip route replace 192.168.200.0/24 via 10.0.0.2
# on R2
ip addr del 192.168.100.2/24 dev eth2 ; ip link set eth2 down
