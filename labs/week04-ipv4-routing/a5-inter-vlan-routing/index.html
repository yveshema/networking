W4·A5 — Routing between VLANs

Time: 45 min · Needs: one Ethernet switch, one OL9 Router, 4 VPCS · GNS3 project: w04-a5-intervlan

The question: week 3 ended with a network deliberately split into two VLANs that could not reach each other, and a promise that a router would fix it. Collect.

Build it

Rebuild week 3's network, but not week 3's switch. In W3·A4 you built the switch by hand, because how a switch keeps VLANs apart was the thing being taught. Here it is not — the router is. So use a plain Ethernet switch and set its ports from a dialog box.

Drop in an Ethernet switch named SW1, right-click it → Configure, and set the ports:

Port Type VLAN
Ethernet0, Ethernet1 access 10
Ethernet2, Ethernet3 access 20

Cable PC1 .11 and PC2 .12 to the VLAN 10 ports; PC3 .13 and PC4 .14 to the VLAN 20 ports. Leave every address in 192.168.10.0/24 for now, exactly as week 3 left them.

Confirm the week 3 result still holds: PC1 → PC2 works, PC1 → PC3 fails.

Predict first

  1. You are about to attach a router. Will PC1 → PC3 work once it is cabled in? ☐ yes ☐ no
  2. What else has to change? _

Part 1 — The addressing has to change first

This is the part students skip.

# PC1, PC2 — VLAN 10
ip 192.168.10.11/24 192.168.10.1        # .12
# PC3, PC4 — VLAN 20
ip 192.168.20.13/24 192.168.20.1        # .14

What just happened

  • Two VLANs must be two subnets. A router forwards between networks, and if both sides are 192.168.10.0/24 there is nothing to forward between — every host would classify every other host as local and never consult a gateway at all.
  • Week 3 kept one subnet across both VLANs deliberately, to prove that the switch defines the segment and the addressing does not. That was a demonstration, not a design. Real VLANs come with their own subnet, and the reason is exactly this.
  • Note the direction of the dependency: the layer-2 decision (which VLAN) forces the layer-3 decision (which subnet), and not the other way round.

Part 2 — Router on a stick

Add an OL9 Router named R1 and cable its eth0 to SW1:Ethernet4. That one port has to carry both VLANs, so set it differently from the others — Configure → Ports:

Port Type VLAN
Ethernet4 dot1q 1

dot1q means "put a tag on everything leaving this port, so the other end can tell the VLANs apart". The VLAN number on a dot1q port is the one exception: traffic in that VLAN leaves untagged. Set it to 1, which nothing else uses, and VLAN 10 and VLAN 20 both leave tagged — which is what R1 needs.

Then, on R1, one physical interface carrying two VLANs:

# on R1
nmcli device set eth0 managed no
ip link set eth0 up

ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20

ip addr add 192.168.10.1/24 dev eth0.10 ; ip link set eth0.10 up
ip addr add 192.168.20.1/24 dev eth0.20 ; ip link set eth0.20 up

sysctl -w net.ipv4.ip_forward=1
ip addr show
ip route show

From PC1: ping 192.168.20.13.

What just happened

  • It works, over a single cable that carries both VLANs.
  • eth0.10 and eth0.20 are sub-interfaces — one physical port, two logical ones, distinguished entirely by the 802.1Q tag you met in W3·A4. The router puts a tag on when sending and reads it when receiving; that 4-byte field is the whole mechanism.
  • ip route show gained two connected routes and you typed neither. As far as the routing table is concerned these are two ordinary attached networks, and nothing about the forwarding decision knows or cares that they share a wire.
  • The arrangement is called router on a stick, and the stick is the trunk.

Part 3 — Watch the tag flip

Capture the SW1↔R1 link — the one carrying both VLANs. From PC1, ping PC3 once, and examine the echo request and the echo reply.

What just happened

  • The request arrives at R1 tagged VLAN 10 and leaves tagged VLAN 20. Same packet, same IP addresses, different tag — and a different destination MAC, because it is now on a different segment (A3's rule, applied on one cable).
  • Both frames are on the same wire, microseconds apart, in different broadcast domains. That is worth sitting with: the separation VLANs provide is entirely a matter of labels that the devices agree to respect.
  • Which is also the honest limitation. VLAN separation is enforced by configuration, not by physics. A misconfigured trunk port re-joins two segments you believed were separate, and nothing physical will tell you.

Part 4 — Separation you can still prove

Capture on PC2's access link (VLAN 10) while PC3 and PC4 (VLAN 20) ping each other, and while PC3 ARPs.

What just happened

  • PC2's cable stays silent throughout. The broadcast domains are still two, and the router did not merge them — it connected them at layer 3 while leaving layer 2 untouched.
  • So you now have both properties at once: broadcast isolation from the VLANs, reachability from the router, and a single point where traffic between the two groups can be inspected, filtered or refused.
  • That last point is the real reason organisations do this. Once all inter-VLAN traffic goes through one device, that device can have a policy — which is where firewalling lives in every campus network you have used.

If it went wrong

Symptom Cause Fix
Router reachable in one VLAN only Ethernet4 is still an access port Configure → Ports — it must be type dot1q
Nothing works after adding sub-interfaces eth0 itself is down ip link set eth0 up before the sub-interfaces
ip link add ... type vlan fails 8021q module not loaded modprobe 8021q
Hosts reach the router but not each other forwarding off sysctl net.ipv4.ip_forward
Everything worked before you added the router all four ports are in the same VLAN check the port table: 0–1 in VLAN 10, 2–3 in VLAN 20
Trunk capture shows one VLAN untagged the trunk's VLAN is set to 10 or 20 set Ethernet4 to VLAN 1 — its own VLAN is the one that leaves untagged
Cannot find the port settings you placed an Ethernet hub, not a switch a hub has no VLANs; delete it and place a switch
