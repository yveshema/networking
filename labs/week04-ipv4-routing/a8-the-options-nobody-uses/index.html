W4·A8 — The options nobody uses, and why that is the lesson

Time: 45 min · Needs: A4 finished; a NAT node for part 4 · GNS3 project: w04-base (continue) · Extension activity

The question: The IPv4 header can grow. It was designed to carry extra instructions — record your path, timestamp each hop, take a route I choose. Those features still work here and are effectively dead everywhere else. Finding out why explains more about how networks evolve than the features themselves ever could.

Predict first

  1. How large can an IPv4 header be? _ How large is the one you have been looking at all week?
  1. If a packet records the address of every router it passes, how many can it hold? _
  2. Will ping -R work to an address on the real internet? ☐ yes ☐ no · Why? _

Do this — make the header grow

# on PC1
ping -c1 -R 192.168.200.10

Capture it. Find the IHL field in the IP header of both the request and the reply.

What just happened

  • IHL is 4 bits, counting 32-bit words. Minimum 5 — that is the 20-byte header you have used all week. Maximum 15. So the header can reach 60 bytes and no further: 40 bytes for options, for all time.
  • Record Route spends 3 bytes on its own bookkeeping and 4 on each address. (40 − 3) ÷ 4 = 9 addresses, maximum, ever, on any path.
  • Every router on the path appended its own address as your packet went by. The network described its own path, as a designed feature — no tricks, no assumptions, no TTL games.

Do this — the ceiling gets worse

# on PC1
ping -c1 -T tsonly    192.168.200.10
ping -c1 -T tsandaddr 192.168.200.10

Entries recorded by tsandaddr: _

What just happened

  • Address and timestamp is 8 bytes per hop, so the same 40-byte budget holds four.
  • Nine hops was generous in 1981. Four was never generous. A path across the modern internet is routinely fifteen or twenty hops, so these options could not describe the network they were built to describe — even if everything else about them had gone perfectly.

Do this — the option that got them banned

# on R1 and R2
sysctl -w net.ipv4.conf.all.accept_source_route=1

# on PC1
traceroute -g 192.168.100.1 192.168.200.10

Then turn it off and repeat:

# on R1 and R2
sysctl -w net.ipv4.conf.all.accept_source_route=0
# on PC1
traceroute -g 192.168.100.1 192.168.200.10
Worked with accept_source_route=1? ☐ yes ☐ no
Worked with accept_source_route=0? ☐ yes ☐ no
Default value on a fresh system

What just happened

  • The sender chose the path. Not the routers — the sender, from outside the network, deciding which links its packet would traverse.
  • Nearly every protection a network has rests on an assumption about where traffic came from: this arrived on the outside link so treat it as untrusted; that arrived on the inside link so trust it more. If the sender controls the path, it controls which link its packet appears to arrive on, and every one of those assumptions can be deliberately arranged to be wrong.
  • Which is why the default is 0 on every modern system, and why networks discard these packets on sight rather than trusting anyone's configuration.

Do this — the lab is not the internet

First, store PC1's address. It has been 192.168.100.10 since A2, set with ip addr add, which means it exists only in PC1's running kernel. A NAT node hands out addresses, and a card with nothing stored can be handed one — which would take w04-base's addressing apart during an extension activity, in a project five other activities depend on.

# on PC1
nmcli con add type ethernet ifname eth0 con-name lan1 \
      ipv4.method manual ipv4.addresses 192.168.100.10/24 ipv4.gateway 192.168.100.1
nmcli con up lan1

That distinction — a change to the running machine, versus a stored configuration NetworkManager keeps the running machine matching — is W3·A8, part 1.

Now attach a NAT node to SW1, LAN1's switch, so PC1 has a route out, then:

# on PC1
ping -c1 -R 192.168.200.10        # inside the lab, from part 1
ping -c1 -R 1.1.1.1               # the real internet

What just happened

  • Same command, same protocol, two different worlds. Your lab implements the standard faithfully. The internet does not, and has not for a long time.
  • Nothing is broken and no rule was violated. Every operator between you and that address made a local, individually sensible decision to discard or ignore packets carrying options — and the sum of those decisions removed a documented capability from reality without anyone withdrawing it from the specification.
  • This is the activity. Everything before it was setup for this comparison.

Do this — two traceroutes, one winner

You have now built the same thing twice:

A4's traceroute A8's Record Route
Mechanism rig TTL to expire early, collect the complaints ask the network to write its path down
Designed for this job? no — a side effect of a loop-prevention counter yes, explicitly
Hop limit none 9
Needs routers to do anything new? no yes
Works on the internet today yes, universally no

What just happened

  • The elegant, purpose-built, standards-blessed mechanism lost completely to a hack that abuses a loop counter.
  • It won for one reason: it asks the network for nothing new. It requires no cooperation, no capability, no permission. It needs routers to do the single thing they already do when a packet runs out of hops — complain — and it therefore works through equipment that has never heard of traceroute and would refuse it if asked.
  • That is the general rule, and it is worth more than any of the options in this activity: mechanisms that require the network to cooperate die; mechanisms that exploit what the network already does survive.

Read reading-why-protocol-extensions-die.md before the next session. It takes this from one header field to the way the whole internet now evolves — and it explains why the newest transport protocols encrypt almost everything about themselves.
