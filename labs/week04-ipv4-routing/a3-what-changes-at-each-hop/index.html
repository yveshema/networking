W4·A3 — What changes at each hop ★

Time: 45 min · Needs: A2's topology, working in both directions · GNS3 project: w04-base (continue)

The question: one packet crosses three links to get from PC1 to PC2. Which parts of it are the same on all three, and which are different on every one?

Have your week 1 PDU table in front of you. This activity is that table, in motion.

Collect the addresses first

You cannot read the captures without these. Twelve values; get them all before you start.

# on each of PC1, R1, R2, PC2
ip addr show
ip link show
Node Interface IP MAC
PC1 eth0 192.168.100.10
R1 eth0 192.168.100.1
R1 eth1 10.0.0.1
R2 eth1 10.0.0.2
R2 eth0 192.168.200.1
PC2 eth0 192.168.200.10

Predict first

PC1 pings PC2. For the echo request, on each of the three links:

Src MAC Dst MAC Src IP Dst IP
PC1 ↔ R1
R1 ↔ R2
R2 ↔ PC2

Fill it in from your address table before capturing. Guessing wrong here is the point.

Do this

Start captures on all three links simultaneously. Then:

# on PC1
ping -c1 192.168.200.10

Find the echo request in each capture and fill the table in again, from observation.

What just happened

  • The two IP addresses are identical on all three links. Source 192.168.100.10, destination 192.168.200.10, from end to end. Neither router touched them.
  • Both MAC addresses are different on every link, and none of the six values appears twice. PC1's MAC exists only on the first link; PC2's only on the last.
  • So PC1 and PC2 never learn each other's MAC addresses, ever. They cannot: MACs have no meaning beyond one segment, and there are three segments here.
  • Layer 3 addressing is end-to-end. Layer 2 addressing is hop-by-hop, rewritten completely at every router. That is not an implementation detail; it is why the two layers exist separately, and your week 1 table is the picture of one moment in that process.

Do this — confirm it from the hosts

# on PC1
ip neigh show

# on PC2
ip neigh show

What just happened

  • PC1 holds R1's MAC. PC2 holds R2's MAC. Neither holds the other's, and neither ever will, however long you ping.
  • This is W2·A2 part 3 again, now with the full path visible. The frame PC1 sent was addressed to R1 at layer 2 and to PC2 at layer 3 — two destinations, in one frame, meaning different things.
  • The everyday consequence: "can you ping it?" and "is it on your network?" are completely different questions, and the ARP cache answers the second.

Do this — what else changed

Compare the IP header of the same echo request across the three captures, field by field. Two things differ.

What just happened

  • TTL decreased by one at each router. Started at 64 (Linux), 63 after R1, 62 after R2. Decrementing it is a router's obligation, and A4 is about what it is for.
  • The header checksum changed on every link. It has to: it covers the TTL field, so a router that changes the TTL must recompute it. Every router on the internet does this arithmetic for every packet.
  • Nothing else moved. Not the addresses, not the identification, not the payload. A router touches the smallest possible number of fields — everything else it forwards untouched, because everything else belongs to the endpoints.

Do this — the reply, for symmetry

Same three captures, now reading the echo reply.

What just happened

  • Every MAC pair reversed, per link, independently. Every IP pair reversed, once, end to end.
  • The reply's TTL started fresh at 64 from PC2 and arrived at PC1 as 62. The two directions count down separately, because they are separate journeys that happen to use the same wires.

Record

The completed three-link table, prediction and observation side by side, plus:
Times the source IP changed
Times the source MAC changed
MAC in PC1's ARP cache for PC2
TTL on link 1 / link 2 / link 3
Header fields a router modified

One sentence each: what is layer-3 addressing for, and what is layer-2 addressing for?

If it went wrong

Symptom Cause Fix
Only two captures show the packet routing broken again re-check A2 part 3's route on R2
MACs look identical across links you are reading the same capture twice check each Wireshark window's title bar
TTL is 128, not 64 a non-Linux stack somewhere note the value; the decrement is what matters
PC2's MAC appears in PC1's ARP cache the two are on the same segment — cabling error re-check the topology; there must be a router between them
Cannot find the request in a capture too much other traffic filter on icmp
