W2·A6 — Sharing one wire

Time: 35 min · Needs: three OL9 Lab Nodes + an Ethernet switch · GNS3 project: w02-a6-sharing

The question: two conversations, one wire. Packet switching and circuit switching are two answers to that, and they are usually taught as history. Here they are two tc commands, and you can measure the difference.

Build it

H1 .11, H2 .12, SRV .13, all /24, all on one Ethernet switch, nmcli device set eth0 managed no first on each.

On SRV, something worth downloading:

dd if=/dev/zero of=/tmp/big.bin bs=1M count=50
cd /tmp && python3 -m http.server 8080

SRV's single cable is the shared wire. Everything below happens on it.

Predict first

The wire runs at 10 Mbit/s. H1 starts a download. Halfway through, H2 starts one too.

  1. What happens to H1's download? ☐ stops ☐ slows ☐ unaffected
  2. What does H2 get? ☐ nothing until H1 finishes ☐ half ☐ full speed
  3. If H2 never starts, should H1 get the whole 10 Mbit/s? ☐ obviously ☐ not necessarily

Do this — cap the shared wire

On SRV, in a second console:

tc qdisc add dev eth0 root tbf rate 10mbit burst 32kbit latency 400ms
tc qdisc show dev eth0

Now, one flow at a time. On H1:

curl -o /dev/null http://192.168.10.13:8080/big.bin

Record the average speed curl prints. Then run it on H1 and H2 simultaneously — count down out loud, or paste both commands and press enter together — and record both.

What just happened

  • Both downloads ran at once, and each got roughly half. Neither waited for the other, neither was refused, and the sum stayed at the link's capacity.
  • Nothing negotiated that split. The two flows' packets simply interleaved on the wire, each one independently addressed and independently forwarded. Capture the link and you will see frames from both conversations alternating with no pattern and no reservation.
  • That is packet switching. The wire is shared per-packet, allocation is emergent, and nobody asked permission. Its virtue is that H1 alone got the whole link — no capacity was set aside for a conversation that was not happening.
  • Its cost is that neither flow got a promise. Add ten more hosts and everyone's speed falls; nothing breaks, everything degrades. That trade is the whole design.

Do this — reserve capacity instead

Replace the shared cap with a reservation per host — half the link each, and a hard ceiling so neither can borrow from the other:

# on SRV
tc qdisc del dev eth0 root

tc qdisc add dev eth0 root handle 1: htb default 30
tc class add dev eth0 parent 1:  classid 1:1  htb rate 10mbit ceil 10mbit
tc class add dev eth0 parent 1:1 classid 1:10 htb rate 5mbit  ceil 5mbit
tc class add dev eth0 parent 1:1 classid 1:20 htb rate 5mbit  ceil 5mbit
tc class add dev eth0 parent 1:1 classid 1:30 htb rate 1mbit  ceil 1mbit

tc filter add dev eth0 protocol ip parent 1: prio 1 u32 \
   match ip dst 192.168.10.11/32 flowid 1:10
tc filter add dev eth0 protocol ip parent 1: prio 1 u32 \
   match ip dst 192.168.10.12/32 flowid 1:20

tc -s class show dev eth0

Repeat all three measurements.

H1 speed H2 speed Sum
H1 alone —
H2 alone —
Both at once

What just happened

  • H1 alone now gets 5 Mbit/s, not 10. Half the wire sat idle, reserved for a conversation that did not exist. Nothing was broken; the capacity was simply not available to anyone else.
  • With both running, each still got 5 — exactly what each got alone. The arrival of a second flow changed nothing for the first.
  • That is circuit switching's bargain: capacity is allocated in advance, so performance is predictable and unaffected by other traffic — and unused capacity is wasted rather than shared.
  • The telephone network worked this way for a century, and its failure mode is the one you have met: not a slow call, but no dial tone. When the circuits are gone they are gone, however idle they are.

The comparison

Packet switched (tbf) Circuit switched (htb with ceilings)
One flow, half the link idle uses it all wastes it
Second flow arrives first flow slows first flow unaffected
Guarantee offered none exact
Failure mode under load everything degrades new conversations refused
Who decides the split nobody whoever wrote the config

Neither is correct. The internet chose the left-hand column because most traffic is bursty and idle reservations are ruinously expensive at scale — and it has been reinventing the right-hand column ever since, under names like QoS, DiffServ and traffic shaping, whenever something needed a promise.

Record

Both measurement tables, the comparison filled in, and one sentence: your video call and your backup upload share one link. Which column do you want, and for which of the two?

Clean up

tc qdisc del dev eth0 root

If it went wrong

Symptom Cause Fix
Speeds nowhere near 10 Mbit/s virtual links are fast; tbf burst too small raise burst to 64kbit; the ratio between rows matters, not the absolute number
Both flows get the full rate you shaped the wrong direction tc shapes egress; the download leaves SRV, so it must be on SRV's eth0
Reserved test behaves like the shared one filters not matching tc -s class show dev eth0 — the class counters must be non-zero
Simultaneity is hard to arrange human reaction time run the longer transfer first (count=200) so overlap is easy
