W2·A1 — Hub vs switch ★

Time: 35 min · Needs: 4 VPCS, an Ethernet hub, an Ethernet switch (both need dynamips, §0a), Wireshark on the client · GNS3 project: w02-a1-hub-vs-switch

The question: a hub and a switch have the same shape, the same ports and the same cables. What is actually different?

Build it

Four VPCS on one Ethernet switch (Browse Switches), PC1…PC4 on ports Ethernet0…3.

# PC1 / PC2 / PC3 / PC4
ip 192.168.10.11/24        # .12 / .13 / .14
save

One subnet, no gateway, no router, and no configuration on the switch at all. Confirm PC1 can ping all three others.

Predict first

PC1 pings PC2. You are watching PC3's cable, and PC3 is not involved in any way.

  1. How many of the four packets appear on PC3's cable? _
  2. Same question, with a hub in place of the switch. _

Write both numbers down now.

Do this — the switch, watched from a bystander

  1. Right-click the PC3↔SW1 link → Start capture.
  2. On every PC: clear arp
  3. On PC1: ping 192.168.10.12
  4. Read Wireshark. Then run the ping again and read it again.

What just happened

  • PC3's cable carried the ARP request only — destination ff:ff:ff:ff:ff:ff. Nobody knows where PC2 is yet, so the question goes to everybody.
  • It did not carry the ARP reply, and did not carry either ICMP packet. Those are addressed to a specific MAC, and by then the switch knew which port that MAC was behind.
  • The second ping put nothing at all on PC3's cable. The ARP caches were warm, so not even the broadcast was needed.
  • That contrast — broadcast arrives, unicast does not — is the entire behaviour of a switch, measured from a machine that is not in the conversation.

Do this — the hub, same everything else

  1. Delete SW1. Browse Switches → place an Ethernet hub where it was. Re-cable PC1…PC4.
  2. Repeat exactly: capture on PC3's link, clear arp everywhere, ping 192.168.10.12 from PC1, twice.

What just happened

  • PC3's cable carried everything: both ARP frames, and every echo request and reply between PC1 and PC2. The second ping was just as loud as the first.
  • No learning, no table, no filtering. A hub is an electrical repeater — a signal arriving on one port is regenerated out of every other port, and it has no idea what a MAC address is.
  • So every port is one collision domain: only one host can usefully talk at a time, and the wire's capacity is shared by everyone rather than given to each pair.
  • PC3 received traffic addressed to somebody else, in full. On a hub, every machine can read every conversation. This is not a security weakness in some deployments of hubs; it is what a hub is.

This is real. Those frames genuinely arrived on PC3's wire. Nothing was animated for you.

Do this — where the switch keeps what it knows

Put the switch back. Then right-click SW1 → Configure.

What just happened

  • There is nothing to see. Per-port VLAN settings and nothing else — no MAC table, no CLI, no console.
  • Every observation you just made had to be taken from outside the device, because GNS3's Ethernet switch offers no way in. That is a limitation of this switch, not of switches.
  • Week 3 replaces it with a Linux bridge, where the table you have been inferring can be printed, flushed and watched refilling.

One sentence: what does the switch know after the first ping that it did not know before?

If it went wrong

Symptom Cause Fix
"Could not find Dynamips" both hub and switch are dynamips devices §0a. This is the most common week-2 blocker
No packets at all on PC3's link capture started after the ping it is live, not retrospective — start it first
Switch behaves like the hub you re-cabled to a hub and forgot check the icon; hub and switch icons differ
ARP never reappears caches stayed warm clear arp on every node, not just PC1
VPCS ping rejects your flags build differences plain ping 192.168.10.12 works on every build
