W2·A5 — Topology as failure modes

Time: 40 min · Needs: 4 VPCS, an Ethernet hub, two Ethernet switches, Wireshark · GNS3 project: w02-a5-topology

The question: topologies are taught as shapes to memorise. Shapes are not the point — what breaks, and what everyone can overhear, are the point.

Predict first

For each of the three builds below, predict before building:

Frames a bystander sees Hosts lost if the centre fails Hosts lost if one edge cable fails
Bus (hub)
Star (switch)
Star with a redundant link

Build 1 — Bus, approximated by a hub

Four VPCS on an Ethernet hub, 192.168.10.11….14/24.

# on each PC
ip 192.168.10.11/24

Capture on PC3's link. From PC1: ping 192.168.10.12. Then delete the PC4↔hub cable and re-test PC1↔PC2. Then stop the hub itself.

What just happened

  • Every frame reached every host. One shared medium, one collision domain, and no privacy between stations.
  • Losing one edge cable cost exactly one host. Losing the hub cost all four.
  • A real bus was worse than this: one cable with taps, where a single break severed the segment into two halves that could not hear each other. The hub is a bus with the failure mode improved and the overhearing intact.

Build 2 — Star, with a switch

Replace the hub with an Ethernet switch. Same addressing. Repeat all three tests.

What just happened

  • A bystander sees broadcasts only — A1's result, arrived at from a different direction.
  • Edge-cable failure: still one host, same as the bus.
  • Centre failure: still everything. The star did not fix that, and this is the honest finding. A star is not more resilient than a bus; it is more private and it isolates collisions. Those are real gains and they are not this one.
  • The redundancy question is therefore still open, which is what Build 3 is for.

Build 3 — Add a redundant link

  1. Add a second Ethernet switch SW2. Move PC3 and PC4 to it.
  2. Link SW1↔SW2. Confirm all four PCs ping each other.
  3. Now add a second link between SW1 and SW2, for redundancy.
  4. Ping PC1 → PC3 again. Watch the GNS3 link indicators and any capture you have running.

Stop this one quickly. Delete the second inter-switch link as soon as you have seen the effect. It will not damage anything, but it will make the topology unusable and can load your machine.

What just happened

  • The network collapsed. One broadcast entered the loop, was flooded by both switches to each other, was flooded again, and multiplied without limit. A capture fills faster than it can be read.
  • Nothing decremented anything. There is no TTL in an Ethernet frame — that field exists at layer 3, and week 1's teardown showed you exactly where. A looping frame at layer 2 has nothing to stop it.
  • So redundancy at layer 2 is not free and not additive. Adding a cable made the network worse than having no redundancy at all.
  • The fix has a name and a whole activity in week 3: spanning tree, a protocol whose entire job is to find loops and switch them off, keeping them available for the day a link dies.

Symptom Cause Fix

GNS3 becomes unresponsive during Build 3 the loop is doing its job delete a link; if the GUI will not respond, stop the nodes from the toolbar
Cannot delete a link cable tool still armed press Esc, then right-click the link → Delete
Pings fail in Build 3 even after removing the loop switch tables are scrambled stop and start both switches
