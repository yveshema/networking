W2·A4 — NAT from both sides

Time: 45 min · Needs: three OL9 Lab Nodes (the router needs 2 adapters), Wireshark · GNS3 project: w02-a4-nat

The question: the router at home has one public address and a dozen devices behind it. Which address does the internet see, and why can nothing on the internet start a conversation with your laptop?

Build it

   inside 192.168.10.0/24                 outside 203.0.113.0/24

   INSIDE ────────── eth0  NATRTR  eth1 ────────── OUTSIDE
   .11                .1            203.0.113.1     203.0.113.5

NATRTR needs Adapters = 2. On all three nodes, nmcli device set ethN managed no first.

# NATRTR
ip addr add 192.168.10.1/24  dev eth0 ; ip link set eth0 up
ip addr add 203.0.113.1/24   dev eth1 ; ip link set eth1 up
sysctl -w net.ipv4.ip_forward=1

# INSIDE
ip addr add 192.168.10.11/24 dev eth0 ; ip link set eth0 up
ip route add default via 192.168.10.1

# OUTSIDE
ip addr add 203.0.113.5/24 dev eth0 ; ip link set eth0 up

Deliberately do not give OUTSIDE a route back to 192.168.10.0/24. That omission is the experiment.

Predict first

  1. INSIDE pings OUTSIDE. Does it work, given OUTSIDE has no route back? ☐ yes ☐ no
  2. Now turn NAT on. Same question. ☐ yes ☐ no
  3. OUTSIDE tries to ping INSIDE. Does that work? ☐ yes ☐ no

Do this — without NAT

Capture on both links at once — INSIDE↔NATRTR and NATRTR↔OUTSIDE. Then:

# on INSIDE
ping -c2 203.0.113.5

What just happened

  • No replies. Both captures explain it together: the echo request appears on both links, so the router forwarded it correctly and OUTSIDE received it. OUTSIDE generated a reply to 192.168.10.11, consulted its routing table, found nothing, and dropped it.
  • The failure is one-directional and invisible from the sender. INSIDE sees silence and cannot distinguish "not delivered" from "no route home". Two captures can; one cannot.
  • Remember this shape. Week 4's headline activity is the same failure on a bigger topology.

Do this — turn NAT on

# on NATRTR
nft add table ip nat
nft 'add chain ip nat postrouting { type nat hook postrouting priority 100 ; }'
nft add rule ip nat postrouting oifname "eth1" masquerade

nft list ruleset

Both captures still running. On INSIDE:

ping -c2 203.0.113.5

What just happened

  • It works now, and OUTSIDE still has no route to 192.168.10.0/24. Nothing was added to OUTSIDE.
  • Compare the two captures for the same ping:
inside link outside link
source 192.168.10.11 203.0.113.1
destination 203.0.113.5 203.0.113.5
  • The router rewrote the source address in the IP header on the way out and restored it on the way back. OUTSIDE never learned that INSIDE exists; it held a conversation with the router.
  • This is a layer-3 device editing a layer-3 header — genuinely different from anything in A1 or A2, both of which forwarded packets unaltered. The end-to-end principle, that addresses mean the same thing everywhere, has just been broken on purpose.

Do this — read the translation table

# on NATRTR, immediately after a ping
grep -c . /proc/net/nf_conntrack
cat /proc/net/nf_conntrack

What just happened

  • One line per conversation, recording both the original and the translated addressing. The router must remember, because a reply arriving for 203.0.113.1 is meaningless unless it can be matched back to 192.168.10.11.
  • So NAT is stateful, and a hub, a switch and a plain router are not. This box now has a memory that fills up, times out, and can be exhausted.
  • Entries have a timeout. Wait, re-run, and watch them disappear.

Do this — try to get in

# on OUTSIDE
ping -c2 192.168.10.11

What just happened

  • It fails, and it cannot be made to work by adding a route — try it: ip route add 192.168.10.0/24 via 203.0.113.1 on OUTSIDE and ping again. Still nothing useful, and the conntrack table is why. There is no entry, so the router has no idea which inside host a packet for 203.0.113.1 belongs to.
  • NAT is asymmetric by construction. Outbound creates state; inbound requires state that only outbound can create.
  • That asymmetry is why NAT is so often mistaken for a firewall. It is not one — it blocks unsolicited inbound traffic as a side effect of not knowing where to send it, which is a very different thing from a policy decision, and it is exactly the misunderstanding this activity exists to prevent.

If it went wrong

Symptom Cause Fix
nft syntax error on the chain line shell ate the ; keep the single quotes exactly as written
Nothing changes after the rule forwarding off sysctl net.ipv4.ip_forward must be 1
/proc/net/nf_conntrack missing module not loaded yet it loads with the first NAT rule; send a ping first
Works even before NAT you gave OUTSIDE a return route remove it; the missing route is the point
Both captures look identical you captured the same link twice check the link names in the Wireshark title bars

Sidebar — the iptables form

Older material and much of the internet writes this rule as:

iptables -t nat -A POSTROUTING -o eth1 -j MASQUERADE

On OL9 that command is a compatibility front-end that programs the same nftables engine. Both work; nft is what the system actually runs.
