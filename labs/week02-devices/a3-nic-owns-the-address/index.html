W2·A3 — The NIC owns the address

Time: 25 min · Needs: two OL9 Lab Nodes on a switch · GNS3 project: w02-a3-nic

The question: where does a MAC address live, and who decides what it is?

Build it

H1 and H2, OL9, on an Ethernet switch. 192.168.10.11/24 and .12/24, nmcli device set eth0 managed no first on both. Confirm they ping.

Predict first

  1. Where is your MAC address stored? ☐ the OS ☐ the network card ☐ the switch ☐ a server
  2. Can you change it? ☐ yes ☐ no
  3. If you did, who would need to find out, and how would they?

Do this — read it

# on H1 and H2
ip link show eth0

Take the first three bytes of each MAC — the OUI, the Organisationally Unique Identifier — and look them up (ieee.org's OUI listing, or Wireshark's own resolution in the packet list).

What just happened

  • The address was there before you configured anything, and you never chose it. Compare with the IP address, which did not exist until you typed it in week 1.
  • The OUI identifies the manufacturer, and the remaining three bytes are that manufacturer's serial number for the adapter. The address is globally unique by administrative agreement, not by any technical mechanism — vendors buy OUIs and promise not to reuse the tail.
  • Your OUI will resolve to a virtualisation vendor, not a card maker, because these NICs are emulated. That is honest and worth noticing: the "hardware" address of a virtual machine is assigned by software, which is a hint about how firm any of this really is.

Do this — change it

Start a capture on H1's link. On H2, note the current state:

# on H2
ping -c1 192.168.10.11
ip neigh show

H2 now holds H1's MAC. On H1:

ip link set eth0 down
ip link set eth0 address 02:11:22:33:44:55
ip link set eth0 up
ip link show eth0

Back on H2, immediately:

ip neigh show
ping -c1 192.168.10.11
ip neigh show

What just happened

  • The address changed, in software, in one command. "Burned-in" has not been literally true for a long time — the card holds a default and the OS may override it.
  • H2's first ip neigh show still listed the old MAC, marked REACHABLE or STALE. H2 had no way to be told; nobody announces a MAC change.
  • The ping still worked, and the capture shows why: H2 sent to the stale address, got nothing, the entry aged into FAILED, and H2 re-ARPed. The cache is self-correcting, but only by timing out — there is a window during which H2 is confidently wrong.
  • 02: is not in any OUI database. The second-least-significant bit of the first byte is the locally administered flag, and setting it is how you say "I made this up, do not look for a vendor". Check your own: 02 = 0000 0010.

Do this — see it from the switch's side

If A1's topology is still around, put H1 and H2 on the Ethernet switch with two VPCS bystanders, capture on a bystander's link, and change H1's MAC again while pinging.

What just happened

  • The switch had learned the old MAC on H1's port and has no idea it is gone. Frames for the old address keep going to that port until the entry ages out — 300 seconds by default.
  • The new address is learned the instant H1 transmits, because switches learn from source addresses on arriving frames. The switch was never told anything; it overheard.
  • Week 3 prints that table and watches this happen line by line.

If it went wrong

Symptom Cause Fix
RTNETLINK: Device or resource busy interface still up ip link set eth0 down first
Cannot assign requested address odd first byte = multicast bit set first byte must be even; 02 is the conventional choice
Ping fails and stays failed switch's table still holds the old address wait for ageing, or ping from H1 once to teach it immediately
MAC reverts after a reboot you used ip, which does not persist nmcli con modify eth0 802-3-ethernet.cloned-mac-address 02:11:22:33:44:55
ip neigh never shows the stale entry you looked too late run it immediately; the window is short
