Routing — Why static routing stops scaling

Time: 50 min · Needs: four OL9 Routers, 2 VPCS, 2 Ethernet switches · GNS3 project: rp-a1-static-limits

The question: static routes work. You built them in week 4, they are predictable, they need no protocol and they never do anything surprising. So why does no real network of any size use them? Count, and find out.

No new commands in this activity. Everything here is week 4's ip route add. What is new is the arithmetic, and it is the arithmetic that makes the case for everything after it.

Predict first

  1. Four routers in a ring, each with a LAN. How many static route statements does the whole network need? _
  2. You add one new LAN. How many routers do you have to edit? _
  3. A link in the ring fails. There is another way round. How long until traffic uses it? _

Topology

              LAN1                            LAN2
             10.1.0.0/24                     10.2.0.0/24
                 │                               │
                 R1 ─────── 10.255.12.0/30 ───── R2
                 │                               │
        10.255.14.0/30                    10.255.23.0/30
                 │                               │
                 R4 ─────── 10.255.34.0/30 ───── R3
                 │                               │
              LAN4                            LAN3
             10.4.0.0/24                     10.3.0.0/24

Four OL9 Routers in a ring, each carrying one LAN. The four links between routers are point-to-point cables with nothing else on them — that is what a /30 is for. Each LAN, though, is a switch with the router on one port, so put a switch on LAN1 and another on LAN3 and hang PC1 and PC3 off them — diagonally opposite, so their traffic has to cross the network. LAN2 and LAN4 have no hosts in this activity and need no switch. Every router needs sysctl -w net.ipv4.ip_forward=1.

Address everything, but write no routes yet.

Do this — count before you type

Before configuring anything, fill this in on paper:
Total networks in the topology (LANs + transit links)
Networks each router is directly connected to
Therefore, static routes needed per router
Total static route statements for the network

What just happened

  • Eight networks: four LANs and four transit links. Each router touches three of them — its own LAN and two transit links — and needs a route for the other five.
  • Twenty route statements, on four routers, for a network with four sites. Every one of them is typed by a person, and every one of them is a chance to type 10.2.0.0 where you meant 10.3.0.0.
  • Now do the arithmetic for a real campus: thirty routers and sixty networks. You are not going to do that by hand, and more importantly you are not going to do it correctly by hand.

Do this — build it anyway

Write the routes. All twenty. Time yourself.

# on R1 — example: reaching LAN3, the far side of the ring
ip route add 10.3.0.0/24 via 10.255.12.2

Confirm PC1 can reach PC3.

What just happened

  • It works, and it is completely deterministic. There is no protocol running, no packets exchanged between routers, no state to converge. Every forwarding decision in this network was made by you, in advance.
  • That determinism is a genuine virtue and it is why static routes still exist — on a default route out of a small office, on a link where you want no surprises. The problem is never that static routing is wrong. The problem is what happens next.

Do this — add one network

Add LAN5, 10.5.0.0/24, on R1. Count the edits.

What just happened

  • R1 gets it for free — a connected route appears the moment you address the interface, which you saw in W2·A2.
  • Every other router in the network needs a new statement. Three edits for one network, and none of them are on the device that changed.
  • That is the property that ends static routing: the work of adding a network is proportional to the size of the network, not to the size of the change. Adding one LAN to a thirty-router campus is twenty-nine edits, on twenty-nine devices, all of which have to be right.

Do this — break the ring

Start a continuous ping from PC1 to PC3, then fail the link R1↔R2:

# on R1
ip link set <the R2-facing interface> down

What just happened

  • The ping stops, and it does not come back. There is a perfectly good path — R1 → R4 → R3 — and it is up, and it is idle.
  • Nothing is going to use it. R1's route to 10.3.0.0/24 says via 10.255.12.2 and that is what it will keep saying, because a static route is a statement about intent, not about reachability. It has no idea the link is gone.
  • Recover it by hand: change the route on R1, and on R2, and on any router whose path to anything went through that link. Time this too.
  • You have met this argument before. In W3·A5 you bought a redundant cable, watched it save you, and then noticed that a human had to notice the failure and act. This is the identical problem one layer up: the redundancy is real, the recovery is manual, and manual recovery means the outage lasts as long as it takes a person to arrive.

The case, in one table

Static routes What you want instead
Adding a network edit every other router edit the router that changed
A link fails outage until a person retypes routes the network finds another way
Who knows the topology you, in your head and your notes the routers, from each other
Chance of a typo proportional to network size one config per router, once
Behaviour under change none — it is a fixed statement recomputed automatically

A routing protocol is what fills the right-hand column. Routers tell each other what they are connected to, each builds its own picture of the network, and each computes its own routes from that picture — continuously, so that a change anywhere is reflected everywhere without anybody typing.

The next activity is the first half of that: before any route can be learned, two routers have to discover each other and agree to talk. That turns out to be where most real problems live.

Record
Networks / directly connected / routes per router / total
Minutes to configure twenty static routes
Edits required to add one LAN, and on which devices
What happened to the ping when the ring broke
Why the idle path was not used
Minutes to recover by hand

Two sentences: static routing failed here for two different reasons. Name both, and say which one would hurt more in a building you are on call for.

If it went wrong

Symptom Cause Fix
Ping works one way only a route exists outbound but not on the return path W4·A2 — every path needs a route in both directions
Some pairs work, others do not a missing statement among the twenty ip route show on each router and check against your count
Ping fails between directly connected routers forwarding off, or wrong mask on the /30 sysctl net.ipv4.ip_forward; /30 gives exactly two usable addresses
Ping recovers on its own after the break you left a route via R4 from an earlier attempt that is a redundant static route, which is worth noticing — but check it is deliberate
PC has no route anywhere no default gateway on the VPCS ip 10.1.0.10/24 10.1.0.1
