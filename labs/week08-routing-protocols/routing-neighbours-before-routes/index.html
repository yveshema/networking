Routing — Neighbours come before routes

Time: 60 min · Needs: the ring from the previous activity · GNS3 project: rp-a1-static-limits (continue in it)

The question: you are about to turn on a routing protocol and watch routes appear. Before that happens, something else has to happen first, and it is the part that breaks in the real world. Two routers on the same cable have to find each other and agree to exchange information. Watch them negotiate, then break the negotiation on purpose.

Predict first

  1. Two routers running OSPF on the same wire. What has to be true before either learns a route? ___
  2. What do they send each other before any route information moves? _
  3. If the two ends disagree about something, do you get wrong routes or no routes? _

Do this — clear the decks

Remove every static route you wrote in the previous activity, on all four routers:

# on each router — delete the twenty statements
ip route flush proto static
ip route show

Confirm PC1 can no longer reach PC3. You are starting from a network that is correctly cabled, correctly addressed, and cannot deliver anything beyond its own segments.

Do this — the smallest possible OSPF

The course image ships BIRD. It is configured by one file and controlled with birdc. On R1, replace /etc/bird.conf with:

log syslog all;
router id 10.255.12.1;

protocol device { }

protocol direct {
    ipv4;
    interface "eth*";
}

protocol kernel {
    ipv4 { export all; };
}

protocol ospf v2 {
    ipv4 { import all; export all; };
    area 0 {
        interface "eth0" { stub yes; };
        interface "eth1";
        interface "eth2";
    };
}

Six blocks, and none of them is decoration:

Block What it decides
router id this router's name inside the protocol — an identifier, not an address it listens on
protocol device keeps BIRD's view of local interfaces up to date; without it nothing notices a link change
protocol direct brings the router's own connected networks into BIRD, so OSPF has something to advertise
protocol kernel copies what OSPF learns into the kernel's routing table — the thing ip route show prints
area 0 which OSPF area these interfaces belong to; everything here is in the backbone
stub yes advertise this network, but send no hellos on it — correct for a LAN with no routers on it

stub yes on eth0 is worth pausing on. Without it, R1 sends OSPF hellos onto the LAN where the only listeners are PCs and, in a hostile network, anybody who fancies being told the topology.

Check the file parses before you commit to it, then start it:

# on R1
bird -p -c /etc/bird.conf
systemctl enable --now bird
birdc show protocols

Repeat on R2, R3 and R4, changing router id and the stub/non-stub interface names to match each router's wiring.

Do this — watch two routers meet

Start a capture on the R1↔R2 link before starting BIRD on R2, then start it and run this on R1 repeatedly:

# on R1
birdc show ospf neighbors

What just happened

  • The neighbour moved through a sequence of states, and it is worth having seen them go past:
State What is happening
Down / Init I have heard a hello, but it did not mention me
2-Way I have heard a hello that lists my router ID — we can both hear each other
ExStart / Exchange agreeing who speaks first, then summarising what each of us knows
Loading asking for the details I am missing
Full we hold identical information about this area
  • No route is learned until Full. Everything before it is negotiation, and a neighbour stuck at any earlier state produces exactly the same symptom as no protocol at all: a router that looks configured and knows nothing.
  • In the capture, find the Hello packets. Note two things: they go to 224.0.0.5, a multicast address meaning all OSPF routers, and they are neither TCP nor UDP — the IP header's protocol field says 89, and OSPF rides directly on IP with no transport layer at all. It provides its own reliability, which is why it can afford to.
  • Read one hello. It carries the sender's router ID, its area, its hello and dead intervals, its network mask, and a list of neighbours it has heard from. Almost every field in it is a thing that has to match, which is the subject of the rest of this activity.

Now check the routes:

# on R1
birdc show route
ip route show

PC1 can reach PC3 again, and you typed no routes to make that true.

Do this — break it four ways

Each of these is a real failure that occurs in real networks. Do them one at a time, and each time run birdc show ospf neighbors and note which state it sticks at.

1. A mismatched subnet. Change R2's address on the R1 link to 10.255.99.2/30.

2. A mismatched hello interval. On R2, set interface "eth1" { hello 5; }; — R1 is still using the default 10.

3. A mismatched area. On R2, put the R1-facing interface in area 1 instead of area 0.

4. A mismatched MTU. Put everything back, then: ip link set eth1 mtu 1400 on R2 only.

What just happened

  • 1, 2 and 3 never get past Init or fail to appear at all. The hello was heard and rejected. Two routers refuse to become neighbours unless they agree on the subnet, the timers and the area, because a disagreement about any of those means they disagree about what network they are on.
  • 4 is the interesting one. The adjacency reaches ExStart or Exchange and sticks there — the hellos matched perfectly, so the routers found each other, agreed to talk, and then failed while trying to exchange databases. Nothing about the symptom points at MTU.
  • That is the failure worth memorising. A neighbour stuck at ExStart/Exchange with correct addressing and correct timers is, in practice, almost always an MTU mismatch — often caused by a tunnel or a VLAN tag added somewhere in the middle by somebody else.
  • Note the general shape: the protocol fails safe. In every one of the four cases you got no routes rather than wrong routes. A router that cannot agree with its neighbour declines to learn from it, which is a much better failure than confidently forwarding into a black hole.

Put everything back and confirm all four neighbours reach Full.

Record
Neighbour states you observed, in order
The state at which routes begin to exist
Destination address and IP protocol number of a hello
Four things that must match, from reading one hello
Which break stuck at ExStart/Exchange, and why that is hard to guess
Wrong routes or no routes?

One sentence: what does stub yes prevent, and why would you want that on a LAN?

If it went wrong

Symptom Cause Fix
bird will not start config syntax bird -p -c /etc/bird.conf prints the line
No neighbours at all interfaces not listed, or all marked stub birdc show ospf interface — the transit links must not be stub
Neighbours Full, but ip route show unchanged no protocol kernel export ipv4 { export all; } inside protocol kernel
Routes exist for transit links but not LANs protocol direct missing without it the router's own networks are never advertised
Two routers share a router id copied the config without editing it IDs must be unique; BIRD will complain in the log
MTU break does not stick some builds tolerate the mismatch check birdc show ospf interface for the MTU each side believes; the lesson stands either way
Everything breaks after a reboot bird not enabled systemctl enable --now bird
