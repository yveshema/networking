Routing — Convergence, and choosing which way round

Time: 55 min · Needs: the ring, with OSPF running on all four routers · GNS3 project: rp-a1-static-limits (continue in it)

The question: the first activity ended with a broken ring, an idle spare path, and a stopwatch running while you retyped routes. Do it again with OSPF on, and find out what changed. Then take control of which path the network picks, because "it works" and "it goes the way you intended" are different claims.

Predict first

  1. The R1↔R2 link fails. How long until PC1 can reach PC3 again? _
  2. What decides whether traffic goes clockwise or anticlockwise around the ring? _
  3. Two paths of identical length. Which is used? _

Do this — everyone knows everything

Before breaking anything, look at what the four routers are holding:

# on R1, then on R3
birdc show ospf state

What just happened

  • The two outputs describe the same network. Not similar — the same. Every router in an area holds an identical database of who is connected to what, because each one floods a description of its own links to everybody and relays what it receives.
  • Each router then computes its own routes from that shared picture, by working out the shortest path from itself to everywhere. That is why the protocol family is called link-state: what gets distributed is the state of the links, not a list of routes.
  • This is the structural difference from static routing. You never described the topology to any router. They described themselves to each other, and every one of them derived the answer.

Do this — break the ring again

Continuous ping from PC1 to PC3, then:

# on R1
ip link set <the R2-facing interface> down

Count the lost packets. Then bring it back and count again.

What just happened

  • It recovered on its own, in about a second. Compare that with the number you wrote down in the first activity, where recovery was measured in minutes and required you to be present, awake and correct.
  • traceroute from PC1 to PC3 now and you will see the traffic going the other way round the ring, through R4. Nobody chose that. Every router recomputed, arrived at a consistent answer, and installed it.
  • You have seen this shape before. W3·A5 ended with a blocked port taking over automatically when a cable failed, and the argument was identical: the redundancy was already paid for, and the protocol removes the human from the recovery. This is the same bargain one layer up.

Do this — the two speeds of failure

The recovery above was fast because the interface went down and the router noticed instantly. That is not the only way a link fails. Simulate the other kind — the link stays up, but the router at the far end stops answering:

# on R2
systemctl stop bird

Time it again.

What just happened

  • This took far longer — around 40 seconds, not one. The link never went down, so R1 had no event to react to. It had to wait until it had heard no hello from R2 for the dead interval, which defaults to four times the hello interval.
  • These are the two failure modes every network has, and they behave completely differently:
What the router sees Recovery
Cable pulled, interface down carrier loss, immediately ~1 second
Far end silent, link still up nothing — only the absence of hellos up to the dead interval
  • The second is why "the link is up" is not evidence that anything works, and why lowering hello and dead intervals is a normal tuning decision on links that matter. It is not free: shorter timers mean more hellos and a greater chance of declaring a neighbour dead during a brief hiccup.

Start BIRD on R2 again.

Do this — where the path preference comes from

# on R1
birdc show ospf interface

Find the cost of each interface.

What just happened

  • Each interface carries a number, derived by default from its bandwidth: a fast link gets a low cost, a slow link a high one. OSPF adds these up along each candidate path and picks the lowest total.
  • This is exactly the mechanism from W3·A5. There, each link had a cost from its speed, costs were summed along the path to the root, and the lowest total won. Same idea, same direction — lower is better — implemented independently at a different layer for a different purpose. Two protocols built decades apart reached for the same tool.
  • The difference is what the number is measured to. Spanning tree measures distance to one elected root. OSPF measures distance from each router to every destination, separately, which is why there is no root here and no blocked links.

Do this — take control of the path

Right now PC1 → PC3 goes one way round. Make it go the other way, without unplugging anything.

On R1, raise the cost of the interface facing R2:

    area 0 {
        interface "eth1" { cost 500; };
        ...
    };

# on R1
birdc configure
traceroute 10.3.0.10        # from PC1

What just happened

  • The path moved, and every router agreed about it, because you changed a number that all of them were told about. You did not configure a route anywhere.
  • This is the layer-3 twin of setting the bridge priority in W3·A5. Left alone, the path is whatever the default costs happen to produce — which is to say, an accident of interface speeds. Set deliberately, it is a decision you can point at in a design document.
  • Real reasons to do this: one path is metered and the other is not; one crosses a link you are paying for by the gigabyte; one goes through a firewall you want traffic to pass. None of those are visible to a protocol that only knows bandwidth.
  • Set the two paths to equal cost instead and look at ip route show. You will get both next-hops in one route — equal-cost multipath — and traffic is shared between them. Note that this is a thing spanning tree specifically cannot do: at layer 2 the second path must be blocked, and at layer 3 it can be used. That is a real advantage of routing over bridging, and a reason large networks push the layer-3 boundary as close to the edge as they can.

If it went wrong

Symptom Cause Fix
No recovery at all the other side of the ring was never adjacent birdc show ospf neighbors on all four — you need Full all the way round
Recovery takes 40 s even for a cable pull the interface did not actually go down in GNS3, ip link set … down on the router is reliable; suspending the link may not be
birdc configure reports no change you edited the file on the wrong router check the router id in the file you edited
Cost change has no effect the other path is still cheaper raise it further, or read the totals with birdc show route all
Equal-cost paths do not appear kernel multipath, or costs not actually equal birdc show ospf interface on both; the totals must match exactly
Routes vanish after birdc configure a syntax error left the protocol down birdc show protocols, then bird -p -c /etc/bird.conf
