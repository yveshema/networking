W5·A2 — The asymmetric mask ★

Time: 45 min · Needs: one OL9 Router, two OL9 PCs, one Ethernet switch, Wireshark · GNS3 project: w05-a2-asymmetric

The question: A1 changed one host's mask and broke it in one direction. What does a network look like when two hosts on the same wire disagree about the mask — and it still works?

This is the failure that a subnetting worksheet cannot teach you and that you will meet in the field.

Build it

              192.168.10.0/24
   H1 ────┐
          SW1 ──── R1:eth0  192.168.10.1/24
   H2 ────┘        R1:eth1  203.0.113.1/24 ── (nothing; it exists to be a gateway)

# R1 — correct, and it is the only device that is
for i in eth0 eth1 eth2 eth3; do nmcli device set $i managed no; done
ip addr add 192.168.10.1/24 dev eth0 ; ip link set eth0 up
ip addr add 203.0.113.1/24  dev eth1 ; ip link set eth1 up
sysctl -w net.ipv4.ip_forward=1
sysctl -w net.ipv4.conf.all.send_redirects=0        # so the symptom is not hidden

# H1 — correct
ip addr add 192.168.10.11/24 dev eth0 ; ip link set eth0 up
ip route add default via 192.168.10.1

# H2 — the mistake: /25, everything else identical
ip addr add 192.168.10.200/25 dev eth0 ; ip link set eth0 up
ip route add default via 192.168.10.1

H2's mask is wrong. Nothing else in this network is.

Predict first

  1. H1 pings H2. Works? ☐ yes ☐ no
  2. H2 pings H1. Works? ☐ yes ☐ no
  3. If both work, is anything wrong?

Do this — test both directions

# on H1
ping -c2 192.168.10.200

# on H2
ping -c2 192.168.10.11

What just happened

  • Both directions work. A network with a definite misconfiguration, passing every test anyone would normally run.
  • This is why the fault survives to production. ping says yes, users say yes, and the mask stays wrong for years.

Do this — find it anyway

Capture the R1↔SW1 link — the router's link, which nobody would think to watch for traffic between two hosts on the same switch. Then run both pings again.

Appears on R1's link?
H1 → H2
H2 → H1

And ask each host what it thinks it is doing:

# on H1
ip route get 192.168.10.200
# on H2
ip route get 192.168.10.11

What just happened

  • H1 → H2 never touched the router. H1 believes .200 is local — under /24 it is — so it ARPs for it and sends directly.
  • H2 → H1 went through the router. Under /25, H2's subnet is 192.168.10.128–.255, and .11 is outside it. H2 classified its own next-door neighbour as a foreign network and sent the packet to its gateway, which sent it straight back out of the same interface to H1.
  • ip route get confirms it in one line per host: H1 reports a direct route, H2 reports via 192.168.10.1.
  • The two directions of one conversation took different paths. That is the signature of a mask mismatch, and it is visible from neither endpoint — it took a capture on a third device, exactly as in W4·A2.
  • Note what the router did: it forwarded the packet back out of the interface it arrived on, which is a strong hint that something upstream is confused. Real routers send an ICMP redirect here, saying "you did not need me". send_redirects=0 above suppresses that so you could see the raw symptom; turn it back on and watch the redirect appear.

Do this — make it hurt

The fault is invisible while the router is available. Remove that:

# on R1
ip link set eth0 down

Then, from H1: ping -c2 192.168.10.200, and from H2: ping -c2 192.168.10.11.

What just happened

  • H1 → H2 still works. It never needed the router.
  • H2 → H1 fails completely. Its path depended on a device that has nothing to do with a conversation between two hosts three feet apart on the same switch.
  • The misconfiguration was latent. It cost nothing until an unrelated component failed, and then it produced a failure whose obvious explanation ("the router is down") is wrong — the router was never supposed to be involved.
  • Half-working networks are worse than broken ones. A broken network gets fixed on the day it breaks.

Bring it back: ip link set eth0 up.

Do this — find it the fast way

If you suspected this on a real network, the diagnosis is two commands, not a capture:

# on every host on the segment
ip addr show eth0 | grep inet

What just happened

  • The masks are right there and they do not match. The check is trivial once you know to make it, and impossible to stumble on if you do not — which is the entire value of having seen the symptom.
  • Add it to your own checklist: when traffic between two hosts on one segment behaves asymmetrically, compare the masks before anything else.

Record
H1 → H2
H2 → H1
H1 → H2 on the router's link
H2 → H1 on the router's link
ip route get on H1 / on H2
Both directions with R1's eth0 down

Two sentences: why did every normal test pass, and what is the one-command check?

If it went wrong

Symptom Cause Fix
Both directions bypass the router H2's mask is not actually /25 ip addr show — delete the old address first
H2 → H1 fails from the start no default route on H2, or forwarding off on R1 add the route; sysctl net.ipv4.ip_forward
Traffic stops matching after a while ICMP redirects taught H2 a host route sysctl -w net.ipv4.conf.all.send_redirects=0 on R1, ip route flush cache on H2
Router's link shows nothing at all wrong link captured capture R1↔SW1, not a host link
Both directions fail .200 is outside /25's range in your build /25 covers .128–.255; .200 must be in it and .11 must not
