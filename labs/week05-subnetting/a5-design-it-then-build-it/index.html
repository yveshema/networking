W5·A5 — Design it, then build it ★

Time: 90 min, or one session plus homework · Needs: 1 OL9 Router, 4 hosts, 4 Ethernet switches · GNS3 project: w05-a5-design · Graded as a lab

The question: everything so far gave you the addresses. Now you choose them, and somebody else has to be able to build your network from what you wrote down.

The brief

You have been allocated one block: 172.16.40.0/24. Nothing else. You may not request more.

Segment Hosts required now Growth expected
OFFICE 50 to 60
LAB 20 to 25
SERVERS 6 none
MGMT 2 none
Transit to the upstream router 2 none

Constraints:

  1. No overlap. Every subnet disjoint from every other.
  2. Each subnet must fit its growth figure plus the router's own address, and be the smallest prefix that does. A segment planned for 6 hosts needs 7 usable addresses — the router lives in the subnet too. Being off by one here is the most common error in this exercise, and it is invisible until the day the last host is added.
  3. Contiguous from the bottom of the block. State the unused remainder as the smallest set of CIDR blocks that covers it exactly — it will not be one block, and working out why is part of the question.
  4. .1 of each subnet is the router. Hosts start at .10 except where the subnet is too small.
  5. The transit subnet has a router at each end and no hosts, so 2 usable addresses is enough.

Part 1 — The plan (do this before touching GNS3)

Allocate largest first. This is not a style preference: allocating a small subnet into the middle of the block fragments it and can make a later large one impossible even when enough addresses remain.

Segment Hosts needed + router Prefix Network First usable Last usable Broadcast Spare
OFFICE 60 61
LAB 25 26
SERVERS 6 7
MGMT 2 3
Transit 2 2
Unused remainder — — — — — —

Check before you build:

  • [ ] Every prefix is the smallest that fits its growth number plus one for the router
  • [ ] No two ranges overlap — check each boundary against the next network address
  • [ ] Total allocated + remainder = 256 addresses exactly
  • [ ] Each usable count ≥ the "+ router" column, not the "hosts needed" column
  • [ ] The remainder is expressed as properly aligned CIDR blocks, not as a range

Answer in writing: why does allocating largest-first matter? Give a specific ordering of these five subnets that would waste addresses or fail outright.

Part 2 — Build it

One OL9 Router. Each segment — OFFICE, LAB, SERVERS and MGMT — gets its own Ethernet switch, named SW-OFFICE, SW-LAB, SW-SERVERS and SW-MGMT, with one host on it. (The transit subnet has no hardware in this lab — configure it on a spare interface or record it as reserved, and say which you did.)

Use nmcli, not ip. The project expects configuration that survives a reboot, and this is the rehearsal:

# on the router, per segment
nmcli device set eth0 managed no
nmcli con add type ethernet ifname eth0 con-name office \
      ipv4.method manual ipv4.addresses 172.16.40.1/26
nmcli con up office

Then hosts, then sysctl -w net.ipv4.ip_forward=1.

Part 3 — Prove it

Evidence, not assertion. For each claim, the command output that supports it:

Claim Evidence to attach
Every host reaches its own gateway ping from each host
Every host reaches every other segment ping matrix, 4 × 4
The router has exactly the intended connected routes ip route show
Each host agrees with your plan about its own subnet ip route get for an address just outside it
A broadcast does not leave its segment capture on another segment's link during ping -b
Boundaries are where you said ip route get for the last address in each subnet and the first of the next

../../scripts/collect-report.sh gathers most of this into one text file per node. Use it.

Part 4 — Peer review (the part that teaches the most)

Swap plans with another student. Build their network from their document only — no conversation, no clarifying questions. Then report:
Could you build it without asking anything?
Anything ambiguous, and how you resolved it
Anything wrong — overlap, wrong size, wrong boundary
One thing their document did better than yours

What just happened

  • Almost every plan is unambiguous to its author. The gaps show up only when someone else builds it — a missing gateway convention, a prefix stated in one notation in one row and another notation elsewhere, a "spare" range whose ownership is unstated.
  • That is why address plans are documents with conventions, not just tables of numbers. On a real network the person building it is you, eighteen months later, and you will remember none of this.
  • A plan that requires a conversation has failed, even if the arithmetic is perfect.

Marking

Marks
Plan: arithmetic correct, no overlaps, smallest fitting prefixes 30
Plan: written justification of largest-first allocation 10
Build matches the plan exactly 20
Evidence: all six claims supported by command output 25
Peer review completed, specific and fair 15

Note where the marks are: half of them are for the plan and the evidence, not the build. A working network you cannot document or prove is worth less than a documented one with a fixable fault.

If it went wrong

Symptom Cause Fix
Subnets do not add up to 256 a boundary is off by one recompute each network address as previous + block size
A host cannot reach its gateway host outside its own subnet ip route get from the host
nmcli con up fails device still managed, or name collision nmcli device set ethN managed no; nmcli con show
The remainder is fragmented you allocated smallest-first reallocate largest-first; this is Part 1's question, answered the hard way
Peer's network will not build ambiguity, not necessarily error record exactly where you had to guess — that is the deliverable
