IPv6 — The address you already have

Time: 40 min · Needs: two OL9 PCs on one Ethernet switch · GNS3 project: v6-a1-linklocal

The question: you have not configured IPv6 anywhere in this course. Before you type anything, find out whether your machines already have IPv6 addresses — and if they do, where those came from and what they are for.

Predict first

  1. Does an interface you never configured for IPv6 have an IPv6 address? ☐ yes ☐ no
  2. If it does, who assigned it? _
  3. Two machines on one switch, neither configured. Can they ping each other over IPv6? ☐ yes ☐ no

Topology

        192.168.10.0/24  (IPv4, for contrast only)

     H1 ───────── SW ───────── H2
     .11                       .12

An OL9 PC at each end of a GNS3 Ethernet switch. Give them IPv4 addresses as usual, so you have something familiar beside the new thing. Configure no IPv6 at all.

Do this — look before you build

# on H1
ip -6 addr show dev eth0

What just happened

  • There is an address there, and you did not put it there. It begins fe80:: and it appeared when the interface came up.
  • Every IPv6 interface gets one of these automatically, always, for as long as the link is up. It is called a link-local address, and IPv6 is not willing to operate without one.
  • Note the two words in the name. Link: it is valid on this one cable and nowhere else. Local: no router will ever forward it. It exists so that two machines sharing a wire can talk before anybody has been given a real address — which turns out to be a prerequisite for almost everything else IPv6 does.
  • Compare this with IPv4, where an interface with no configuration has no address at all and can do nothing. That difference is deliberate and it is the foundation of the next two activities.

Do this — use it

Read H2's link-local address the same way, then from H1:

# on H1 — this will fail
ping -c2 fe80::XXXX:XXXX:XXXX:XXXX

It fails, and the error is the lesson. Now try again with the interface named on the end:

# on H1 — this works
ping -c2 fe80::XXXX:XXXX:XXXX:XXXX%eth0

What just happened

  • Invalid argument, or "no route to host". The address alone was not enough information to send a packet, which is not something IPv4 ever does to you.
  • The reason is that fe80::/64 is not one network — it is the same network on every interface at once. Your machine has that prefix on eth0, and would have it on eth1, eth2 and every other link as well. So "send this to fe80::1234" is genuinely ambiguous: out of which cable?
  • %eth0 is the answer to that question. It is called a zone index or scope identifier, and it is not part of the address — it is a note to your own machine about which door to use. It never appears in the packet.
  • This is the one piece of IPv6 syntax that catches everybody, and now you know it is not a quirk. It is the direct consequence of having an address range that is deliberately reused on every link.

Do this — where did the last 64 bits come from?

# on H1
ip link show dev eth0 | grep ether        # your MAC address
ip -6 addr show dev eth0 | grep fe80      # your link-local

Compare the two. On a current OL9 system they will look unrelated.

Now watch what the older scheme looked like:

# on H1
nmcli con modify <your-connection> ipv6.addr-gen-mode eui64
nmcli con up <your-connection>
ip -6 addr show dev eth0 | grep fe80

What just happened

  • With eui64, the last 64 bits are built directly from the MAC address: split the six bytes in half, insert ff:fe in the middle, and flip one bit in the first byte. Find your MAC inside your address and you have decoded it.
  • That was the original scheme, and it has an obvious problem. Your interface ID would then be the same on every network you ever joined — a permanent, globally unique serial number, broadcast by every packet you sent. Change coffee shops, keep the same second half of your address.
  • So modern systems default to stable-privacy: an interface ID that is stable per network but different on each one, computed from a secret key rather than from hardware. Same address size, same rules, no tracking identifier.
  • Put it back with nmcli con modify <your-connection> ipv6.addr-gen-mode stable-privacy. Note that you have just changed an address without changing any hardware, which is the point.

Do this — one wire, two protocols

Start a capture on the link and, from H1, ping H2 over IPv4 and then over IPv6 link-local.

What just happened

  • Both conversations are on the same cable, in the same switch, at the same time. Nothing had to be chosen between them. A host runs both protocols side by side, and this is how essentially every real network operates today — the phrase for it is dual stack.
  • In the capture, the two look like completely different animals above Ethernet, and completely identical below it. The switch forwarding them has no opinion about either, because it is reading MAC addresses, exactly as in week 3.
  • Look at the EtherType field on each frame: 0x0800 for IPv4 and 0x86DD for IPv6. That single field is how one wire carries two incompatible protocols without ambiguity, and it has been in the Ethernet header since week 1.

If it went wrong

Symptom Cause Fix
No fe80:: address at all IPv6 disabled on the interface or at boot sysctl net.ipv6.conf.eth0.disable_ipv6 must be 0; check for ipv6.disable=1 on the kernel command line
ping says "invalid argument" missing %eth0 the scope identifier is not optional for link-local
%eth0 given but still unreachable you used H1's own address read H2's address on H2, not on H1
Address unchanged after addr-gen-mode the connection was not brought back up nmcli con up <name>; the address is generated at activation
nmcli reports no such connection the interface is unmanaged from an earlier activity nmcli device set eth0 managed yes, or configure it with a fresh connection
Capture shows no IPv6 you pinged the IPv4 address twice check the target begins fe80::
