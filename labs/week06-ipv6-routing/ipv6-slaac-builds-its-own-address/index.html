IPv6 — The host that addresses itself

Time: 45 min · Needs: one OL9 Router, one OL9 PC, one Ethernet switch, Wireshark · GNS3 project: v6-a3-slaac

The question: the previous two activities gave you an address that works on one wire and goes no further. Getting a routable address in IPv4 means either typing one or running a DHCP server. IPv6 has a third answer that needs neither. Watch a host build its own address out of thin air, and work out who told it what.

Predict first

  1. A host with no IPv6 configuration is plugged into a network with a router on it. Does it end up with a routable address? ☐ yes ☐ no
  2. If it does, does a server anywhere record that it handed that address out? ☐ yes ☐ no
  3. Where does its default route come from? _

Topology

       fd00:10::/64

   R1 ───────── SW ───────── CLIENT
   ::1                       (configure nothing)

R1 is an OL9 Router. CLIENT is an OL9 PC you will not configure at all — that is the entire point. Leave it running with its automatic link-local address and nothing else.

Do this — before the router speaks

# on CLIENT
ip -6 addr show dev eth0
ip -6 route show

Write down what is there: one fe80:: address, and a route for fe80::/64 and nothing else. No way off this wire.

Do this — give the router something to announce

# on R1
nmcli con modify <connection> ipv6.method manual \
      ipv6.addresses fd00:10::1/64
nmcli con up <connection>

sysctl -w net.ipv6.conf.all.forwarding=1

Forwarding matters here for a reason beyond routing: a Linux box will not send router advertisements unless it believes it is a router, and this is the switch that decides.

Now start a capture on the link, and turn on advertisements:

# on R1
nmcli con modify <connection> ipv6.method shared
nmcli con up <connection>

Watch CLIENT — without touching it:

# on CLIENT
ip -6 addr show dev eth0
ip -6 route show

What just happened

  • CLIENT now has a second IPv6 address, a routable one, and a default route. Nobody logged into it. Nobody configured it. Nothing was requested from a server.
  • This is SLAAC — stateless address autoconfiguration — and the word doing the work is stateless.

Do this — read the message that caused it

Find the ICMPv6 messages in the capture:

ICMPv6 type Sent by Says
Router Solicitation 133 the host is there a router here?
Router Advertisement 134 the router yes, I am one, and this link uses this prefix

Expand the Router Advertisement and find the Prefix Information option inside it.

What just happened

  • The router announced a prefix — the first 64 bits — and its own presence. That is all it said. It did not name CLIENT, did not choose an address for it, and does not know what address CLIENT ended up with.
  • Compare the prefix in the capture with CLIENT's new address. The first half is the router's prefix; the second half is the interface ID CLIENT already had. The host did the arithmetic itself: here is the network, and I already know who I am, so here is my address.
  • The default route came from the RA too — specifically from the fact that a router sent it. The source address of the advertisement, a link-local address, is what CLIENT installed as its gateway. Check with ip -6 route show and note that your default route points at an fe80:: address, which is why link-local had to exist first.
  • Routers send these unsolicited, every few minutes. The Router Solicitation exists so a host that has just booted does not have to wait for the next one.

Do this — find the lease

Try to find, anywhere on R1, a record of the address CLIENT is using.

# on R1
ip -6 neigh show

What just happened

  • The neighbour table knows CLIENT exists, because they have spoken — that is NDP from the previous activity, not SLAAC. There is no lease, no database, no allocation record, and no server.
  • That is the trade. DHCP knows exactly which machine holds which address, when it expires, and can hand out a different answer per client — at the cost of running a server that must be available, backed up, and made redundant. SLAAC needs nothing but a router that already had to be there, and in exchange nobody can tell you who has which address.
  • Neither is better. Real networks frequently run both: SLAAC for addressing, and DHCPv6 for the things an RA cannot express. The RA has flag bits (M and O in the capture) whose entire job is to tell hosts which combination this network expects.
  • Notice also that CLIENT kept its link-local address. A host does not swap one address for another; it accumulates them, and normal IPv6 machines have several at once.

Do this — take it away again

# on R1
nmcli con modify <connection> ipv6.method manual ipv6.addresses fd00:10::1/64
nmcli con up <connection>

Wait, then check CLIENT again.

What just happened

  • The address does not vanish immediately. Every prefix in an RA carries a valid lifetime and a preferred lifetime, and the host holds the address until those run down.
  • So SLAAC is stateless but not timeless. The router controls how long its announcements are trusted, which is the only lever it has over addresses it never assigned.

If it went wrong

Symptom Cause Fix
No RA in the capture forwarding off, so the box does not consider itself a router sysctl net.ipv6.conf.all.forwarding=1 before enabling advertisements
ipv6.method shared not supported older NetworkManager install and configure radvd with a prefix fd00:10::/64 block on that interface — the observations are identical
CLIENT gets no address RAs are being ignored sysctl net.ipv6.conf.eth0.accept_ra must be 1; on a forwarding host it defaults to 0, so check CLIENT is not itself set up as a router
Address appears but no default route accept_ra is 1 but accept_ra_defrtr is 0 check both sysctls
Two addresses from the same prefix temporary privacy addresses are enabled that is correct behaviour — ip -6 addr marks one temporary; it is a third scheme worth reading about
Address never expires after removing the RA lifetimes not yet elapsed they are minutes, not seconds; check ip -6 addr for the countdown
