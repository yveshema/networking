DHCP — The lease is a loan, with a deadline

Time: 45 min · Needs: the previous activity's topology · GNS3 project: dh-a1-dora (continue in it)

The question: the previous activity ended with PC1 holding an address "for 600 seconds". Nobody took it away after 600 seconds. Find out what that number actually governs, and what happens when the server that granted it disappears.

Predict first

  1. What does PC1 do when its lease is halfway through? _
  2. How many packets does renewing take? _
  3. The server is switched off. When does PC1 lose its address? _
  4. PC1 reboots. Does it get the same address back? ☐ yes ☐ no

Do this — make time run faster

Ten minutes is too long to watch and too short to be realistic, so shrink it. On SRV, change one value in /etc/kea/kea-dhcp4.conf:

    "valid-lifetime": 60,

# on SRV
systemctl restart kea-dhcp4

This is the same trick as shrinking the forwarding table in W3·A6: the mechanism you want to watch runs on a timescale built for real networks, so you compress the timescale rather than the mechanism. Nothing else about the behaviour changes.

On PC1, take a fresh lease and note the second it happened:

# on PC1
nmcli con down dh && nmcli con up dh
date; ip addr show dev eth0 | grep 'inet '

Do this — watch it renew

Start a capture on PC1's link and leave it running for two minutes without touching anything.

What just happened

  • At about 30 seconds — half the lease — PC1 sent a REQUEST and got an ACK. Two packets, not four. There was no DISCOVER and no OFFER.
  • Look at the addresses on those two packets. The renewal is unicast, straight to the server. PC1 has an address now and knows exactly who granted it, so none of the shouting from the first activity is necessary any more.
  • That halfway point has a name: T1, the renewal timer. It is set to 50% of the lease by default, and the reason it is halfway rather than at the end is that it leaves the client another half a lease in which to keep trying if the server does not answer.
  • There is a second timer, T2, at 87.5%. If renewal has failed by then the client stops asking its server and starts broadcasting to any server that will listen — the state is called rebinding. Only when the full lifetime runs out does it give up the address.

So the lease is not a countdown to losing the address. It is a countdown with two alarm clocks before it, and in normal operation you never reach the end.

Do this — take the server away

Leave the capture running.

# on SRV
systemctl stop kea-dhcp4

Now watch PC1 for the next two minutes. Keep pinging SRV from it and note when the address disappears:

# on PC1
watch -n1 'date; ip addr show dev eth0 | grep "inet "'

What just happened

  • Nothing happened immediately. PC1 kept its address and carried on working, because a lease is a grant with a deadline and the deadline had not arrived. This is why a DHCP server can be rebooted in the middle of the day without anybody noticing.
  • In the capture you will see renewal attempts at T1, then more of them, then the broadcast rebinding attempts after T2 — the client escalating from asking my server to asking anybody.
  • At the end of the 60 seconds, the address was removed. PC1 did not keep using it. That is the half of the contract clients are obliged to honour: when the lease expires without renewal, the address goes back, because something else may have been given it in the meantime.
  • Scale this back up mentally. With a realistic lease of 8 or 24 hours, a DHCP outage is invisible for hours and then takes down every client at roughly the same time. The failure is delayed and then sudden, which is a genuinely difficult shape to diagnose if you do not know the mechanism.

Start the server again and let PC1 recover:

# on SRV
systemctl start kea-dhcp4

Do this — hand it back politely

# on PC1
nmcli con down dh

# on SRV
cat /var/lib/kea/kea-leases4.csv

Then bring it back up and look again.

What just happened

  • Shutting the connection down sent a RELEASE, and the server marked the lease as returned rather than waiting out the clock. Find it in the capture — it is a single packet with no reply, because there is nothing to agree about.
  • PC1 got the same address back. The server keyed the record on PC1's client identifier and offered the address it had before, which is why machines appear to have stable addresses on networks where nothing is static.
  • That stability is a courtesy, not a guarantee. It survives a reboot and usually a weekend; it does not survive the address being handed to someone else while you were away. Anything that genuinely must not move — a server, a printer, a switch's management address — gets a reservation on the DHCP server or a static address, and is kept out of the pool.

If it went wrong

Symptom Cause Fix
No renewal in the capture lease still long valid-lifetime must be short — 60 s; restart Kea and re-take the lease
Address never disappears the client renewed successfully confirm Kea is actually stopped: systemctl status kea-dhcp4
Address disappears instantly you brought the connection down rather than waiting nmcli con down releases on purpose; to watch expiry, leave it alone
No RELEASE packet NetworkManager skipped it on an already-dead link release only happens on a clean shutdown of the connection
Different address on return the lease was reclaimed and reissued expected once the pool is under pressure; this is the point about reservations
watch shows no change for minutes lease timers are in seconds but the capture is the better clock read the timing from the capture, not the shell
