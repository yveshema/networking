DHCP — Four packets, and a client with no address

Time: 50 min · Needs: one OL9 Server (SRV), one OL9 PC (PC1), one Ethernet switch, Wireshark · GNS3 project: dh-a1-dora

The question: a machine that has just booted has no IP address. To ask for one it must send a packet. But every packet needs a source address and a destination address, and it has neither. Work out how it asks.

Predict first

  1. What source address can a machine use before it has one? _
  2. What destination address, given that it does not know where the server is? _
  3. How many packets does it take to get an address? _
  4. Why more than two?

Topology

        192.168.10.0/24

   SRV ───────── SW ───────── PC1
   .5 (static)               (nothing)

SRV is an OL9 Server, PC1 an OL9 PC, both on one Ethernet switch. SRV gets 192.168.10.5/24 by hand. PC1 gets nothing — you are going to watch it ask.

Do this — a DHCP server, in eleven lines

On SRV, replace /etc/kea/kea-dhcp4.conf with:

{
  "Dhcp4": {
    "interfaces-config": { "interfaces": [ "eth0" ] },
    "lease-database": { "type": "memfile", "name": "/var/lib/kea/kea-leases4.csv" },
    "valid-lifetime": 600,
    "subnet4": [
      {
        "id": 1,
        "subnet": "192.168.10.0/24",
        "pools": [ { "pool": "192.168.10.100 - 192.168.10.110" } ]
      }
    ]
  }
}

Every line of that is one decision, and none of them is boilerplate:

Setting The decision it records
interfaces-config which wires this server answers on — it will ignore every other one
lease-database where the record of who-has-what is kept, on disk
valid-lifetime how long an address is good for, in seconds — 600 is ten minutes
subnet the network this server believes it is serving
pools the range it is allowed to hand out — eleven addresses, deliberately few

Before you start it, pin SRV's own address. Right now 192.168.10.5 exists only in the running kernel: you typed it with ip addr add, and nothing recorded that you meant it. The moment a DHCP server is running on this wire, SRV's own card can ask for an address and be given one — and the .5 you typed disappears with no warning at all. Write it down instead:

# on SRV
nmcli con add type ethernet ifname eth0 con-name srv \
      ipv4.method manual ipv4.addresses 192.168.10.5/24
nmcli con up srv

ipv4.method manual is the part doing the work. It tells NetworkManager where this card's address comes from, so the card never asks the network. That distinction — a change to the running machine, versus a stored configuration NetworkManager keeps the running machine matching — is W3·A8, part 1.

Check it before starting it, then start it:

# on SRV
kea-dhcp4 -t /etc/kea/kea-dhcp4.conf     # parse only — catches a missing comma before it matters
systemctl enable --now kea-dhcp4
systemctl status kea-dhcp4

Note the subnet is /24 but the pool is eleven addresses. A pool is not a subnet. The server hands out only what is in the pool; everything else in the subnet is left for machines like SRV that are addressed by hand. Overlapping those two is one of the most common ways to break a network.

Do this — watch a machine ask

Start a capture on PC1's link first. Then:

# on PC1
nmcli con add type ethernet ifname eth0 con-name dh ipv4.method auto
nmcli con up dh

ip addr show dev eth0

Filter the capture with bootp — the historical name Wireshark still uses for DHCP.

What just happened

You have four packets, and they have names:

# Name From To Meaning
1 DISCOVER 0.0.0.0 255.255.255.255 is there a DHCP server out there?
2 OFFER SRV broadcast yes — you may have 192.168.10.100
3 REQUEST 0.0.0.0 255.255.255.255 I accept 192.168.10.100
4 ACK SRV broadcast confirmed, it is yours for 600 seconds
  • The source address is 0.0.0.0, which is not an address — it is the absence of one, written down. This is the one situation where sending from it is legal, and the reason DHCP has to be specified so carefully.
  • The destination is 255.255.255.255, the all-hosts broadcast. PC1 cannot address the server directly because it does not know the server exists. So it shouts, and whichever servers are on the segment hear it. Remember from week 3 what a broadcast costs and who receives it — every host on the segment processed this.
  • Why four and not two? Because there might be more than one server, and both would offer. The DISCOVER may draw several OFFERs; the REQUEST names which offer the client is taking, and it is broadcast so that the servers whose offers were not taken hear the rejection and put their addresses back. Two packets would work only on a network you had promised never to grow.
  • Expand any of the four and find the client identifier and the client's MAC address. That is what the server keys its records on. The client has no IP to be identified by, so identity at this stage is a layer-2 identity.

Now look at the server's side of it:

# on SRV
cat /var/lib/kea/kea-leases4.csv

That file is the stateful half of DHCP, and it is the thing SLAAC does not have. The server knows exactly which machine holds which address and until when.

Do this — find out how it got back

Look at the OFFER again, at layer 2 this time.

What just happened

  • The OFFER had to reach a machine that still has no IP address. It cannot be routed and it cannot rely on the client's IP stack accepting a unicast to an address it has not yet configured.
  • So the server broadcasts the reply too, and the client recognises it by matching the transaction ID in the packet against the one it generated for its DISCOVER. Find that field and confirm all four packets share a value.
  • Ports: server on 67, client on 68. Both fixed, both known in advance by every DHCP implementation ever written, because there is no way to discover them — the discovery mechanism is the thing being bootstrapped.

Do this — run out

Bring up nine more clients, or simply repeat on a handful of nodes, until the pool is exhausted. Then ask for one more.

What just happened

  • The eleventh client gets nothing. No error dialog, no address, no route — the same outcome as an unplugged cable, from a completely different cause.
  • A DHCP pool is a fixed resource, and running out is a real and regular outage. It is also invisible from the client, which is why "some machines get on the network and some do not" is a symptom worth recognising immediately.

If it went wrong

Symptom Cause Fix
kea-dhcp4 will not start JSON syntax kea-dhcp4 -t /etc/kea/kea-dhcp4.conf names the line
SRV loses .5 and picks up a pool address its card was never pinned nmcli con show — if there is no srv connection, the address was only ever in running state
Server starts, client gets nothing wrong interface in interfaces-config it must list the interface facing the client
Client gets an address from somewhere else another DHCP server on the segment — possibly the GNS3 host capture and read the OFFER's source; isolate the topology
Only DISCOVERs, no OFFER firewalld on SRV blocking UDP 67 firewall-cmd --add-service=dhcp, or stop firewalld for this activity
No packets at all in the capture capture started after nmcli con up DHCP completes in milliseconds; start the capture first
Client keeps its old address NetworkManager reused a cached lease nmcli con down dh && nmcli con up dh, or delete /var/lib/NetworkManager/*.lease
