DHCP — Crossing a router, and the field that makes it possible

Time: 60 min · Needs: one OL9 PC (PC1), one OL9 Router (R1), one OL9 Server (SRV), 2 Ethernet switches, Wireshark · GNS3 project: dh-a2-relay

The question: DHCP works by broadcasting. Routers do not forward broadcasts — you proved that in week 3 and relied on it in week 4. So a building with twenty subnets needs twenty DHCP servers. It does not have twenty. Find out why not.

Predict first

  1. PC1 broadcasts a DISCOVER. R1 is between it and the server. What reaches the server? _
  2. If something did carry it across, how would the server know which subnet to allocate from? _
  3. And how would the reply get back to a client that still has no address? _

Topology

   10.0.10.0/24                        10.0.30.0/24

  PC1 ──── SW1 ──── R1 ──── SW2 ──── SRV
  (dhcp)          .1  │  .1          .5
                  eth0│eth1
Node Configuration
R1 eth0 10.0.10.1/24, eth1 10.0.30.1/24, both stored (below), sysctl -w net.ipv4.ip_forward=1
SRV 10.0.30.5/24 stored, and a route back: ip route add 10.0.10.0/24 via 10.0.30.1
PC1 nothing — ipv4.method auto

Store R1's and SRV's addresses rather than setting them with ip addr add. A DHCP server is about to start serving this network, and R1:eth0 sits on the very wire the offers cross — a card there with nothing stored can ask for an address and be handed one out of the pool it is supposed to be relaying. PC1 is the exception, and having nothing stored is the entire point of it.

# on R1
nmcli con add type ethernet ifname eth0 con-name client-side \
      ipv4.method manual ipv4.addresses 10.0.10.1/24
nmcli con add type ethernet ifname eth1 con-name server-side \
      ipv4.method manual ipv4.addresses 10.0.30.1/24
nmcli con up client-side ; nmcli con up server-side

# on SRV
nmcli con add type ethernet ifname eth0 con-name srv \
      ipv4.method manual ipv4.addresses 10.0.30.5/24
nmcli con up srv

That distinction — a change to the running machine, versus a stored configuration NetworkManager keeps the running machine matching — is W3·A8, part 1.

That route on SRV is not an afterthought. The server is going to have to answer a client on a network it is not attached to, and it needs a way back.

Do this — try it without help

Put the Kea config from the previous activities on SRV, but for the client's subnet, not its own:

{
  "Dhcp4": {
    "interfaces-config": { "interfaces": [ "eth0" ] },
    "lease-database": { "type": "memfile", "name": "/var/lib/kea/kea-leases4.csv" },
    "valid-lifetime": 600,
    "subnet4": [
      {
        "id": 1,
        "subnet": "10.0.10.0/24",
        "pools": [ { "pool": "10.0.10.100 - 10.0.10.110" } ],
        "option-data": [ { "name": "routers", "data": "10.0.10.1" } ]
      }
    ]
  }
}

# on SRV
systemctl restart kea-dhcp4

Capture both links — PC1–SW1 and SW2–SRV — and:

# on PC1
nmcli con up dh

What just happened

  • PC1's capture has DISCOVERs, repeated, getting no answer. SRV's capture has nothing at all.
  • R1 did exactly what a router does: the destination was 255.255.255.255, which is not an address on any network it forwards to, so it dropped it. This is not a misconfiguration and there is no setting called "forward broadcasts" that you should be looking for.
  • The server, meanwhile, is running correctly, holding a perfectly good pool for 10.0.10.0/24, and will never hear anyone ask for it.

Do this — put a listener on the client's wire

The thing that is missing has to be on PC1's segment, because that is where the broadcast is audible. It is called a relay agent, and its job is to hear DHCP broadcasts locally and forward them as ordinary unicast packets to a server somewhere else.

R1 already has a leg on that segment, so R1 is the natural place for it:

# on R1
dnsmasq --dhcp-relay=10.0.10.1,10.0.30.5 --keep-in-foreground --log-dhcp

Two addresses, and the order matters: the interface to listen on, then the server to forward to. Leave it running in that console.

With both captures still going:

# on PC1
nmcli con down dh && nmcli con up dh
ip addr show dev eth0 | grep 'inet '

What just happened

  • PC1 has an address from a server two networks away, and nothing about PC1 changed. It broadcast, exactly as before, and was not aware that anything unusual happened.
  • Compare the two captures side by side. This is the whole activity:
On PC1's wire On SRV's wire
Source 0.0.0.0 10.0.10.1
Destination 255.255.255.255 10.0.30.5
Delivery broadcast unicast
  • The relay did not tunnel or encapsulate anything. It re-sent the request as its own, from its own address, to a specific server. On SRV's wire this is an ordinary routable packet that any network can carry.

Do this — find giaddr

Expand the DISCOVER as it arrives at SRV and find the field named gateway IP address, giaddr.

What just happened

  • It contains 10.0.10.1 — the address of the relay's interface on the segment the client is on. Not the relay's other address, and not the server's.

  • That single field does two jobs at once, and both are indispensable:

  • It tells the server which subnet to allocate from. SRV has no idea where the client is — the packet arrived on its 10.0.30.0/24 interface like everything else. It looks at giaddr, finds 10.0.10.1 inside its declared 10.0.10.0/24 subnet, and picks from that pool. This is why the config declares the client's subnet and not the server's.

  • It tells the server where to send the reply. The client still has no address, so the answer goes back to giaddr, and the relay does the last step — broadcasting it onto the client's wire, where a machine with no address can receive it.

  • So the relay's address is not a routing detail. It is the client's location, written into the packet, and it is the only thing that lets one server serve twenty subnets correctly.

  • Add a second subnet to the Kea config and a second relay on another segment, and nothing else has to change. That is how a building with twenty networks has one DHCP server and not twenty.

Do this — break it in the instructive way

Change the relay to announce the wrong interface:

# on R1 — stop the relay, then
dnsmasq --dhcp-relay=10.0.30.1,10.0.30.5 --keep-in-foreground --log-dhcp

Try PC1 again.

What just happened

  • The request reaches the server and is refused, or answered from the wrong pool — because giaddr now claims the client is on 10.0.30.0/24, and the server believes it.
  • The server has no independent way to check. It cannot see the client, cannot see the topology, and has exactly one piece of evidence about where the request came from. giaddr is trusted absolutely, which is worth remembering the next time you see a DHCP problem that looks like the server has gone mad.

Put it back the way it was.

If it went wrong

Symptom Cause Fix
Relay starts but nothing is forwarded wrong first address it must be the relay's address on the client's segment
Server receives the request, sends nothing no matching subnet for giaddr the subnet4 entry must contain the giaddr address
Server replies, client never sees it no route back to 10.0.10.0/24 on SRV ip route add 10.0.10.0/24 via 10.0.30.1
dnsmasq refuses to start it is already running as a service systemctl stop dnsmasq first; this activity runs it in the foreground on purpose so you can read its log
Kea ignores the relayed packet not listening on the right interface interfaces-config must name the interface facing R1
Client gets an address from R1 itself you started a DHCP server rather than a relay --dhcp-relay and --dhcp-range are different things; do not set both
Everything works but the client has no gateway option-data missing the routers option is what supplies the default route
