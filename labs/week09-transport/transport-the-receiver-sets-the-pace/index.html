Transport — The receiver sets the pace

Time: 50 min · Needs: one OL9 PC, one OL9 Server, one Ethernet switch, Wireshark · GNS3 project: tr-a4-window

The question: a fast server sends a large file to a slow client. Nothing in IP prevents the server from sending as fast as its network card allows, and nothing in the network tells it not to. So why does the client not simply drown?

Do this after the three-way handshake and the UDP activity. It answers a question those two leave open: TCP does not merely deliver reliably, it delivers at a rate somebody agreed to.

Predict first

  1. A 50 MB file is sent over TCP. How many packets? _
  2. What limits how much the sender may have in flight before hearing back? _
  3. The receiving application stops reading. What happens to the sender? _

Topology

CLIENT .11 (an OL9 PC) and SRV .12 (an OL9 Server) on one Ethernet switch. On SRV:

# on SRV
dd if=/dev/zero of=/tmp/big.bin bs=1M count=50
cd /tmp && python3 -m http.server 8080

Do this — how big is a piece?

Capture the link, then:

# on CLIENT
curl -s -o /dev/null http://192.168.10.12:8080/big.bin

In the capture, find the SYN and look for the MSS option, then look at the size of the data packets that follow.

What just happened

  • The file did not travel as a file. It was cut into thousands of segments, each one small enough to fit in a frame — around 1460 bytes of data apiece.
  • That number is not arbitrary: 1500 bytes of Ethernet payload, minus 20 for the IP header, minus 20 for the TCP header, leaves 1460. It is announced in the SYN as the maximum segment size, so each end learns what the other is prepared to receive before any data moves.
  • You have now met this arithmetic three times. W1·A3 counted what headers cost. W3·A4 showed a VLAN tag adding 4 bytes and pushing a frame to 1522. The OSPF activity showed two routers refusing to become neighbours over an MTU disagreement. Every one of those is the same 1500 bytes, seen from a different layer.
  • Note that MSS is negotiated per connection at setup, and then not revisited. A path that shrinks in the middle later — a tunnel, an extra tag — is the classic cause of a connection that opens perfectly and then hangs the moment real data flows.

Do this — watch the receiver push back

Now make the client read slowly. --limit-rate does not slow the network; it slows the rate at which curl takes data out of its own socket, which is exactly what a busy application does.

Capture again, then:

# on CLIENT
curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin

Let it run for thirty seconds. In Wireshark, look at the Win= value on packets from CLIENT, and watch for packets Wireshark colours and labels TCP ZeroWindow and TCP Window Update.

What just happened

  • Every acknowledgement CLIENT sends carries a window — a number saying this is how many more bytes I can accept right now. It is not a setting. It is the free space left in the receive buffer, reported on every packet.
  • As curl fell behind, that buffer filled and the advertised window shrank, packet by packet. You can watch it count down.
  • When it reached zero, CLIENT sent a ZeroWindow: stop, I have nothing left. And the server stopped — not because of an error, not because of loss, but because it was told to.
  • When curl read some more, CLIENT sent a Window Update and transmission resumed.
  • This is flow control, and the important part is who is in charge. The receiver is. The sender may be idle, the network may be empty, and the transfer still proceeds at exactly the rate the slowest participant can absorb. Nothing in the middle of the network was involved in that negotiation, and nothing in the middle even knows it happened.

Do this — the other brake

Flow control protects the receiver. There is a second, entirely separate mechanism protecting the network, and it is easy to confuse them.

# on CLIENT — run the unlimited download again, and while it runs:
watch -n0.5 "ss -ti '( dport = :8080 )'"

Look for cwnd: and rtt: in the output.

What just happened

  • cwnd is the congestion window — the sender's own private limit on how much it will put in flight, which no one advertises to it. It starts small, grows while things go well, and collapses when a packet is lost.
  • So a TCP sender is limited by two numbers at once, and it obeys whichever is smaller:
Set by Protects Announced?
Receive window the receiver the receiving machine yes, on every packet
Congestion window the sender the network in between no — inferred from loss
  • The second one is inferred, which is worth sitting with. No router ever tells a sender to slow down. The sender guesses, from the fact that a packet went missing, that some queue somewhere overflowed, and backs off. The entire internet's stability rests on every sender voluntarily performing that guess.
  • That also explains the UDP activity's result from a new angle. UDP has neither window. It sends what the application gives it, as fast as the application gives it, and if that swamps a receiver or a link, nothing in UDP will notice or care.

Do this — starve it deliberately

Shrink the receive buffer so the ceiling is visible in one screen:

# on CLIENT
sysctl -w net.ipv4.tcp_rmem='4096 8192 8192'

Repeat the unlimited download and compare the transfer rate and the Win= values with before. Then put it back:

# on CLIENT
sysctl -w net.ipv4.tcp_rmem='4096 131072 6291456'

What just happened

  • The transfer got slower, on an unchanged network, with no loss and no congestion. The receiver simply could not have as much data in flight at once.
  • This is the shape of a real and frequently misdiagnosed performance problem: a connection that cannot go fast because the window is too small for the round-trip time. On a long path the sender spends most of its time waiting for permission, and no amount of extra bandwidth helps.
  • The product of those two numbers — window size and round-trip time — is the most the connection can ever move at once. Everything else is detail.

If it went wrong

Symptom Cause Fix
No ZeroWindow in the capture the client kept up lower --limit-rate to 10k, or shrink tcp_rmem first
No MSS option in the SYN you expanded the wrong packet it is on the SYN and SYN/ACK only, never on later packets
ss -ti shows no cwnd connection already finished use the 50 MB file and run watch during the transfer
Window never changes window scaling makes the raw value misleading Wireshark shows the calculated value; check the scale factor in the SYN
Transfer speed unchanged after tcp_rmem existing connection kept its old buffer the setting applies to new connections; start a fresh curl
Speeds are unrealistically high throughout virtual links have no real bandwidth limit add tc qdisc add dev eth0 root tbf rate 10mbit burst 32kbit latency 400ms on SRV, as in W2·A6
