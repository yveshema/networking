Transport — The address inside the machine

Time: 45 min · Needs: one OL9 Server, one OL9 PC, one Ethernet switch · GNS3 project: tr-a0-ports

The question: an IP address gets a packet to a machine. That machine is running a web server, an SSH daemon, a DNS resolver and your shell. The packet arrives at one network card, once. Something has to decide which program gets it — and it is not IP, because IP has already finished.

This is the first transport activity. Do it before the three-way handshake.

Predict first

  1. Two programs on one machine, one IP address. What tells them apart? _
  2. You open two browser tabs to the same website. How many connections, and how does the machine keep the replies separate? _
  3. Is a connection identified by one number, or by more than one? _

Topology

        192.168.10.0/24

   CLIENT ───── SW ───── SRV
     .11                 .12

An OL9 PC and an OL9 Server on one Ethernet switch. Capture the link for the last section.

Do this — two services, one address

# on SRV — two terminals
python3 -m http.server 8080
python3 -m http.server 9090

# on CLIENT
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.10.12:8080/
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.10.12:9090/

Now look at what is waiting on SRV:

# on SRV
ss -tlnp

What just happened

  • Two servers, one IP address, and every request reached the right one. The IP address was identical in both cases — the only difference in the packet was a 16-bit number, and that number is the port.
  • ss -tlnp lists listening sockets: -t TCP, -l listening, -n numeric, -p the process. Read the Local Address:Port column. Each program has claimed a port and the kernel will hand it anything addressed there.
  • So a port is not a networking concept so much as a delivery address inside one machine. IP gets the packet to the building; the port gets it to the right desk.
  • Two programs cannot claim the same port on the same address at the same time. Try it — start a third server on 8080 and read the error. That collision is why "address already in use" is one of the most common messages in all of computing.

Do this — where does the client's port come from?

Hold two connections open at once. On SRV, make a file worth downloading slowly:

# on SRV
dd if=/dev/zero of=/tmp/big.bin bs=1M count=50

# on CLIENT — two terminals, both at once
curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin
curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin

While both are running:

# on CLIENT
ss -tan '( dport = :8080 )'

# on SRV
ss -tan '( sport = :8080 )'

What just happened

  • Two connections, to the same server, on the same port, from the same client. Everything about them is identical except one field: the client's own port number, which is different for each.
  • The client never chose those numbers. The kernel allocated them from the ephemeral range — a block of high-numbered ports handed out temporarily for the life of a connection and returned afterwards. Check yours:
# on CLIENT
sysctl net.ipv4.ip_local_port_range
  • So ports come in two kinds, and the difference is who has to know them in advance. A server port is fixed and published, because clients must be able to guess it — 80, 443, 22, 53. A client port is temporary and arbitrary, because only the two machines involved ever need to know it.

Do this — count the fields

Look at the ss output again and write out everything that distinguishes one of those connections from the other.

What just happened

  • A connection is identified by four things, not one:
Connection A Connection B
Source IP 192.168.10.11 192.168.10.11
Source port e.g. 41022 e.g. 41024
Destination IP 192.168.10.12 192.168.10.12
Destination port 8080 8080
  • Three of the four are identical. The connections are distinct because the whole four-tuple is distinct, and that is the rule: two connections may share any three of those values, never all four.
  • This is what makes a web server serving ten thousand people simultaneously possible on one port. The port is not the connection. The port is one field of four.
  • Notice the listening socket in ss -tlnp is still there, unchanged, alongside the connected ones. A listening socket does not turn into a connection — it stays listening and spawns a separate connected socket for each client. That distinction is invisible until you look, and it explains how a server accepts a second visitor while the first is still reading.

Do this — see it in the packet

Capture the link and start one more curl. Expand the TCP header of any packet.

What just happened

  • Source port and destination port are the first two fields of the TCP header — the very first four bytes, before sequence numbers, before flags, before anything else. They are that important.
  • Watch them swap between the request and the reply. 41022 → 8080 going out, 8080 → 41022 coming back. The pair reversed is how each end recognises the other's half of the conversation.
  • Look at where the TCP header sits: after the IP header, which is after the Ethernet header. Week 1 took that stack apart; this is the layer you had not yet needed. IP addresses the machine and TCP addresses the program, and both are in every single packet because both questions have to be answered on arrival.
  • UDP has the same two fields in the same place, for the same reason. The demultiplexing job is common to both, and it is arguably the only thing they have in common.

If it went wrong

Symptom Cause Fix
Second http.server fails to start port already claimed that is the lesson — read the error, then use a different port
ss shows nothing the connections finished too quickly --limit-rate 20k keeps them open long enough to look
Both curls show the same client port you ran them one after the other, not together ports are reused once released; run them simultaneously
ss -tlnp shows no process name not run as root sudo ss -tlnp
Connections to 8080 refused server died with its terminal restart it, or background it with &
No TCP header visible in Wireshark you expanded an ARP or ICMP frame filter with tcp.port == 8080
