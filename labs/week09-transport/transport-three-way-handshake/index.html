Transport — The three-way handshake, and what a connection actually is

Time: 45 min · Needs: one OL9 PC, one OL9 Server, one Ethernet switch (or one OL9 PC + week 4's w04-base) · GNS3 project: tr-a1-handshake

The question: IP delivers packets and forgets them. TCP is described as "connection-oriented" — but no wire changes, no router is told anything, and nothing in the network remembers you. So where does the connection exist?

Predict first

  1. Before any data is sent, how many packets cross the wire to establish a TCP connection? _
  2. Where does the connection live — in the network, or somewhere else? _
  3. You connect to a port nothing is listening on. What comes back? _
  4. Same, but a firewall is dropping it. What comes back? _

Topology

CLIENT is an OL9 PC, SERVER an OL9 Server. Capture the CLIENT↔SW1 link for everything below.

Do this — watch a connection begin

# on SERVER
python3 -m http.server 8080

# on CLIENT — start the capture first

What just happened

  • SYN → SYN/ACK → ACK. Three packets, no data in any of them, before a single byte of your request moved.
  • Each side chose an initial sequence number and told the other. Each side acknowledged the other's. That is the entire ceremony: I will start counting here — understood, and I will start counting here — understood.
  • Nothing in the middle was consulted. No router was told a connection exists. The connection is two matching sets of numbers held in memory at the two ends, and nowhere else.
  • Wireshark shows relative sequence numbers by default. Turn that off (Preferences → Protocols → TCP → Relative sequence numbers) to see the real values, which are large and random — deliberately, so an outsider cannot guess them and inject data.

Do this — watch the state change

# on CLIENT, in a second terminal
watch -n0.2 'ss -tan state all "( dport = :8080 or sport = :8080 )"'

# then, on CLIENT
curl -s -o /dev/null http://10.10.0.20:8080/

States you managed to catch: ________

What just happened

  • ESTAB is the state everyone knows. The interesting ones are the ones that flash past: SYN-SENT, SYN-RECV, and after closing, FIN-WAIT, TIME-WAIT.
  • ss is reading the kernel's socket table — the same memory that is the connection. You are looking directly at the thing the network does not have.

What just happened

  • Closing is FIN → ACK → FIN → ACK: each direction is shut down separately, because a TCP connection is really two independent streams that happen to share a socket. One side can stop sending while still receiving.
  • The side that closes first sits in TIME-WAIT for a couple of minutes. That is not a bug and not a leak: it is the socket refusing to be reused while a delayed duplicate packet from the old connection might still arrive and be mistaken for part of a new one.
  • This is why a server you restart may report "address already in use" for a minute or two.

Do this — refused versus filtered

# on CLIENT
curl -m5 http://10.10.0.20:9999/          # nothing listening

# on SERVER
nft add table inet f
nft add chain inet f in '{ type filter hook input priority 0; policy accept; }'
nft add rule inet f in tcp dport 9999 drop

# on CLIENT
curl -m5 http://10.10.0.20:9999/          # dropped instead

What just happened

  • Nothing listening → RST. The server's TCP stack answers immediately: there is no such socket here. curl fails instantly with "connection refused".
  • Dropped → nothing. curl retransmits its SYN and eventually gives up. The delay is the signal.
  • Same outcome for the user, completely different evidence for you. An instant failure means something answered; a slow failure means nothing did. That single distinction resolves a large share of real connectivity complaints, and it is the transport-layer twin of reject versus drop from W4·A6.
