Transport — UDP has no memory

Time: 45 min · Needs: the previous activity's topology · GNS3 project: tr-a2-udp (continue from tr-a1-handshake)

The question: TCP and UDP sit in the same place, in the same slot of the same IP header, carrying the same bytes over the same wire. Textbooks say one is "reliable" and one is not. Break the link and find out what that word actually buys you — and what it costs.

Predict first

  1. Send 1000 lines over TCP with 20% of packets dropped. How many arrive? _
  2. The same over UDP? _
  3. Which transfer finishes sooner? _
  4. Does the sender know, in either case? _

Do this — a baseline, both protocols

# on SERVER
ncat -l 9000       > /tmp/tcp.out &
ncat -u -l 9000    > /tmp/udp.out &

# on CLIENT
seq 1 1000 | ncat    -w2 10.10.0.20 9000
seq 1 1000 | ncat -u -w2 10.10.0.20 9000

# on SERVER
wc -l /tmp/tcp.out /tmp/udp.out
TCP UDP
Lines received

Both should arrive complete. A healthy link hides the entire difference between these protocols, which is exactly why the difference is hard to teach.

Do this — break the link

# on SERVER — 20% of inbound packets discarded
tc qdisc add dev eth0 root netem loss 20%

Truncate the output files, then repeat both transfers.

What just happened

  • TCP delivered everything. Every gap was noticed by the receiver, the missing segment was retransmitted, and the application never learned any of it happened. Look at the capture: you can count the duplicate sequence numbers.
  • UDP delivered roughly 800 lines and neither end mentioned it. The sender believes it sent 1000. The receiver believes it received everything there was.
  • TCP was slower, and not by a little. Reliability is paid for in latency: every loss costs at least one round trip, and TCP also slows itself down on the assumption that loss means congestion.
  • Ordering came free with TCP and not at all with UDP. Sequence numbers are what make both retransmission and reordering possible; UDP has no such field because it has no such ambition.

Do this — where does UDP keep its state?

# on SERVER
ss -uan
ss -tan

What just happened

  • The TCP socket has a state — ESTAB, TIME-WAIT, something. The UDP socket has none to show.
  • There is nothing to be in a state about. UDP has no handshake, no acknowledgement, no sequence numbers, no teardown. A UDP socket is an address the kernel will deliver datagrams to, and nothing more.
  • Which means the only thing UDP adds to bare IP is ports — the ability to have more than one conversation per host — plus an optional checksum. That is the whole protocol. Everything else you associate with "transport" is TCP's contribution, not the layer's.

Do this — why anyone chooses it

# on SERVER
tc qdisc change dev eth0 root netem loss 5% delay 100ms

# on CLIENT — time a small exchange each way
time (echo ping | ncat    -w3 10.10.0.20 9000)
time (echo ping | ncat -u -w3 10.10.0.20 9000)

Clean up: tc qdisc del dev eth0 root on SERVER.

What just happened

  • TCP paid three round trips before the first byte moved — the handshake — and pays again for every loss. UDP paid nothing and sent immediately.
  • For a voice call, a game, or a DNS lookup, a packet that arrives late is worth less than nothing: the moment it described has passed, and waiting for it delayed everything behind it. Retransmission is actively harmful there.
  • So the choice is not "reliable versus unreliable". It is who handles loss — the transport, or the application. UDP does not lack reliability; it declines to provide it, so that the application can decide what loss means.
  • That is why the newest web transport protocols are built on UDP and implement their own recovery on top. They wanted TCP's guarantees without TCP's fixed opinions about how to deliver them — and, as W4's reading describes, they wanted a shape the network would carry without asking questions.
