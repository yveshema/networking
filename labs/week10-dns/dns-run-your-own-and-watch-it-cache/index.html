DNS — Run your own, and find out why changes take a day

Time: 55 min · Needs: one OL9 Server, one OL9 PC, one Ethernet switch, a NAT node · GNS3 project: dn-a3-cache

The question: everyone has been told that a DNS change "takes 24 hours to propagate". Nothing propagates and nothing takes 24 hours. Serve some names yourself, then change one, and find out what that sentence is actually describing.

Predict first

  1. You change a record on the authoritative server. How does the old value reach anybody afterwards?
  2. What decides how long the old value keeps being served? _
  3. You are moving a service next Tuesday. When should you change anything? _

Topology

   CLIENT ───── SW ───── SRV ───── (NAT node, for upstream)
     .11                 .12

CLIENT is an OL9 PC, SRV an OL9 Server. SRV will run dnsmasq, which is small enough to read in one screen and does both jobs this activity needs: it can be authoritative for names you invent, and it caches everything else.

Address both by storing the configuration rather than with ip addr add. The NAT node on this wire hands out addresses, and a card with nothing stored can be handed one — which would take SRV's .12 away mid-activity, showing up as names failing to resolve rather than as an address that changed.

# on CLIENT
nmcli con add type ethernet ifname eth0 con-name lab \
      ipv4.method manual ipv4.addresses 192.168.10.11/24
nmcli con up lab

# on SRV
nmcli con add type ethernet ifname eth0 con-name lab \
      ipv4.method manual ipv4.addresses 192.168.10.12/24
nmcli con up lab

That distinction — a change to the running machine, versus a stored configuration NetworkManager keeps the running machine matching — is W3·A8, part 1. It also gives you the name to use where this activity says nmcli con modify <connection> later on: it is lab.

Do this — serve some names

On SRV, replace /etc/dnsmasq.conf with:

# answer on this interface only
interface=eth0
bind-interfaces

# do not act as a DHCP server — that is a different activity
no-dhcp-interface=eth0

# names we are authoritative for
local=/lab.local/
address=/web.lab.local/192.168.10.20
address=/db.lab.local/192.168.10.21

# how long anyone may cache our own answers, in seconds
local-ttl=30

# where to send everything else
server=1.1.1.1

Each block is one decision:

Line The decision
interface / bind-interfaces which wire this server answers on — never all of them by accident
local=/lab.local/ this zone is mine — do not ask upstream about it, ever
address=/…/ the records themselves
local-ttl how long others may reuse our answers before asking again
server= the resolver to forward everything else to 
# on SRV
systemctl restart dnsmasq
systemctl status dnsmasq

Point CLIENT at it and ask:

# on CLIENT
nmcli con modify <connection> ipv4.dns 192.168.10.12 ipv4.ignore-auto-dns yes
nmcli con up <connection>

dig web.lab.local A

What just happened

  • You are now the authority for a zone. local=/lab.local/ is the line that makes it so: it tells dnsmasq that questions about this zone are answered from its own configuration and never forwarded, so a name that does not exist here returns NXDOMAIN rather than being asked of the internet.
  • That "never forwarded" property is what makes an internal zone private. Without it, every internal hostname anyone looks up leaks to an upstream resolver as a question.
  • Note the TTL in the answer: 30, exactly as configured, and it does not move however many times you ask. An authoritative server states the TTL; it does not count it down.

Do this — watch a cache fill

Now ask about a name you are not authoritative for, twice, and time both:

# on CLIENT
dig example.com A | grep -E 'Query time|IN\s+A'
dig example.com A | grep -E 'Query time|IN\s+A'

What just happened

  • The first query took tens or hundreds of milliseconds — SRV had to do the whole walk from the previous activity. The second took essentially zero.
  • Look at the TTL on the two answers. The first shows the full value from the authoritative server; the second shows a smaller number. Keep asking every few seconds and watch it count down.
  • That countdown is the cache. SRV stored the record along with the moment it expires, and every time it serves the record it reports the time remaining. When the number reaches zero the entry is discarded and the next question triggers a real lookup.
  • So a TTL is not a property of a record so much as a promise about how stale an answer may be. The owner of the name chooses it, and everyone else is entitled to rely on it for that long.

Do this — change a record and watch nothing happen

# on SRV
sed -i 's|address=/web.lab.local/192.168.10.20|address=/web.lab.local/192.168.10.99|' /etc/dnsmasq.conf
systemctl restart dnsmasq

Immediately, on CLIENT:

# on CLIENT
dig +short web.lab.local A

Then ask again every ten seconds until it changes.

What just happened

  • For up to 30 seconds, CLIENT kept getting the old address, from a server that no longer holds it and would never say it again. Nothing was broken. The record you changed was already out in the world, with a promise attached, and the promise had not expired.
  • Note where the stale copy lived: not on SRV. It is in whatever cached it — here the client's own stub resolver, in the real world a chain of caches you have never heard of and cannot contact.
  • This is what "propagation" means, and the word is misleading. Nothing is pushed anywhere. There is no distribution step, no queue, no synchronisation. There is only a set of caches, each holding an answer until its own timer expires, and the change becoming visible to each one at a different moment.
  • Which is why the answer to "how long will this take" is exactly the TTL that was in force when the old record was last handed out — not the TTL now, and not any number the person asking would like.

Do this — plan a change properly

Set the TTL to a realistic value and think about the consequence:

# on SRV — realistic for a stable record
local-ttl=86400

What just happened

Nothing to observe — this one is arithmetic, and it is the operational point the whole activity exists for.

With a 24-hour TTL, an answer handed out one minute before you make a change is valid for another 24 hours. So the sequence that actually works is:

  1. A day or more ahead, lower the TTL — to 60 seconds, say — and wait for the old, long TTL to expire everywhere. Only now is every cached copy short-lived.
  2. Make the change. It becomes visible everywhere within about a minute.
  3. Afterwards, raise the TTL back up, so you are not paying for a lookup on every request forever.

The mistake is doing step 2 first and then wondering why it is taking a day. By then it is too late to help — the long TTL is already out there, and there is no mechanism to recall it.

There is a real trade-off in that number and it is worth stating plainly: a long TTL means fewer queries, faster responses and resilience if your name servers go down; a short TTL means more queries and more dependence on your servers being up, in exchange for being able to change things quickly. Records that never move get long TTLs. Records in front of anything that might fail over get short ones.

If it went wrong

Symptom Cause Fix
dnsmasq will not start port 53 already in use ss -ulnp and look for :53; stop the other resolver, often systemd-resolved
lab.local names do not resolve CLIENT still using its old resolver cat /etc/resolv.conf — it must show 192.168.10.12
resolv.conf keeps reverting NetworkManager rewriting it set ipv4.dns and ipv4.ignore-auto-dns yes on the connection, not the file
Upstream names fail no egress, or server= unreachable confirm the NAT node works: ping 1.1.1.1 from SRV
TTL never counts down you are asking the authoritative server for its own zone the countdown only appears on cached records — use an external name
Change visible instantly TTL already expired, or the client did not cache shorten the window: re-query immediately after the restart
Old value persists far longer than the TTL another cache in the path, or a stub resolver with its own rules systemd-resolve --flush-caches, or query SRV directly with dig @192.168.10.12
