DNS — One name, resolved by hand

Time: 45 min · Needs: one OL9 Server, one OL9 PC, one Ethernet switch, Wireshark · GNS3 project: dn-a1-onename

The question: every address in this course so far has been a number you typed. Nobody types numbers. Somewhere between a name and a packet, something turns one into the other — and it is not part of IP, not part of TCP, and not built into your machine. Find out what it is and where it lives.

Predict first

  1. You type a name into a browser. How many packets cross the wire before the first one addressed to the website? _
  2. Does your machine know any names? ☐ yes ☐ no
  3. If the name lookup fails, what does the error look like — and would you recognise it as a name problem? _

Topology

   CLIENT ───── SW ───── SRV
     .11                 .12

An OL9 Server (SRV) and an OL9 PC (CLIENT) on one Ethernet switch. SRV will become a name server in the third activity; for now it is only somewhere to aim at. You will need dig, from the bind-utils package.

Do this — find out who your machine asks

# on CLIENT
cat /etc/resolv.conf

What just happened

  • One or more nameserver lines, each an IP address. That is the entire configuration: your machine does not resolve names, it asks someone who does, and this file is the list of who.
  • Note what is not here. There is no database of names, no list of websites, nothing downloaded. A machine's knowledge of names is close to zero and is refreshed one question at a time.
  • Note also where this came from. If the interface uses DHCP, that address arrived in the ACK alongside the IP address — go back and find it in a DHCP capture. Name resolution is one of the things DHCP exists to bootstrap, because a machine that has an address but no resolver can reach everything and find nothing.

Do this — ask one question, deliberately

Start a capture, then:

# on CLIENT
dig example.com A

Read the output in four parts, because dig prints the response's actual structure:

Section Contains
QUESTION exactly what you asked — the name, the class, the type
ANSWER the records that answer it
AUTHORITY which servers are responsible for that zone
ADDITIONAL extra records the server thought would save you a round trip

What just happened

  • The question is echoed back in the reply. That is not padding: a resolver may have several queries outstanding at once over a connectionless protocol, and the echoed question plus a matching ID is how it pairs each answer with what it asked.
  • Look at the ANSWER line. It has four fields — name, TTL, class, type — and then the value. The TTL is a number of seconds, and it is the subject of the third activity.
  • In the capture: UDP, port 53, one packet out and one back. No connection, no handshake, no acknowledgement. Name resolution is the single most common thing that happens on the internet and it is done with two datagrams, because setting up a TCP connection to ask a one-line question would cost more than the question is worth.

Do this — ask for different things about the same name

# on CLIENT
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com NS
dig +short example.com A

What just happened

  • The name is not a thing that has an address. It is a key with several kinds of value attached, and you have to say which kind you want:
Type Answers the question
A what IPv4 address?
AAAA what IPv6 address?
MX where does mail for this domain go?
NS which servers are authoritative for this zone?
CNAME this name is really an alias for that name
PTR which name belongs to this address? (the reverse direction)
  • So DNS is not "the thing that turns names into addresses". It is a general distributed lookup system that is mostly used for addresses. Mail routing, service discovery and certificate validation all ride on it.
  • +short prints only the value. Useful in scripts, and useless for learning, because everything interesting is in the parts it hides.

Do this — go behind the resolver's back

# on CLIENT
echo '192.168.10.12 fileserver' >> /etc/hosts
dig fileserver A
ping -c1 fileserver

What just happened

  • dig found nothing — and ping worked. They disagree, and the disagreement is the lesson.
  • dig speaks DNS and only DNS: it sends a query to a name server and reports what comes back. It deliberately does not consult anything local.
  • ping, like almost every normal program, does not speak DNS at all. It asks the C library to resolve a name, and the library follows /etc/nsswitch.conf, which lists sources in order — typically files dns, meaning /etc/hosts is consulted first and DNS only if that misses.
  • So there are two different resolution paths on every machine, and they can give different answers. This is the reason for a whole category of confusing incidents: "DNS is fine, I checked with dig, but the application still goes to the wrong place." Check with getent hosts <name>, which follows the same path a normal program does.
# on CLIENT
getent hosts fileserver

Remove the line from /etc/hosts when you are done.

Do this — see a failure properly

# on CLIENT
dig doesnotexist.example.com A
curl -m5 http://doesnotexist.example.com/

What just happened

  • dig reports status: NXDOMAIN — an explicit answer meaning this name does not exist, which is different from I could not reach a server (SERVFAIL) and from no answer of that type (NOERROR with an empty answer section).
  • curl says "Could not resolve host". That message is worth recognising instantly, because it tells you the failure happened before any packet was addressed to the destination — the network beyond your resolver was never involved, and testing it will waste your time.
  • The general rule this establishes: when something cannot connect, find out first whether it failed to resolve or failed to reach. Those are different problems with different causes and no overlap, and the error messages distinguish them if you read them.
