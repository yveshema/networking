Connection-oriented transport

Time: 45 min

Needs: one OL9 Server, one OL9 PC, one Ethernet switch

GNS3 project: w12-a1-transport

Info

Times listed are approximate and provided as timing guidelines only. Take as much time as you need to complete the activity.

Question

On a machine running multiple services, how is the stream of inbound packets sorted and dispatched so each packet finds its own way to the correct program?

How do these services manage to communicate with their remote clients using the same wire concurrently?

Predict first

  1. What does a computer use to tell apart packets meant for different programs? ______
  2. Are two browser tabs connected to the same website one connection or two? ______
  3. How many numbers are needed to identify a connection? ______

Topology

        192.168.10.0/27

   CLIENT ───── SW ───── SRV
     .11                 .2

Do this — Server setup

On SRV: 

tmux new \; splitw -h \; splitw -v

# in pane 1 (top to the right)
cd /tmp && python3 -m http.server 8080

# in pane 2 (bottom to the right)
cd /tmp && python3 -m http.server 9090

# in pane 0 (to the left)
ss -tlnp

On CLIENT 

tmux new \; splitw -h \; splitw -v

# in pane 1 (top to the right)
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.10.12:8080/

# in pane 2 (bottom to the right)
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.10.12:9090/

What just happened

  • We used Python's http module to launch two web server process, each process bound to a different port.
  • The client was able to access both services by specifying the port number in the request URL. That resulted in two connections, identical in everything except for one number: the port number.
  • ss -tlnp lists listening sockets: -t TCP, -l listening, -n numeric, -p the process. Read the Local Address:Port column. Each program has claimed a port and the kernel will hand it anything addressed there.
  • Thus, a port is like a unit number in an apartment building. The postman drops mail in the mailbox bearing the unit number of the person the mail is addressed to, and the person will take the mail from the mailbox at a later time when ready.
  • Two programs (including different instances of the same program) cannot claim the same port number

Do this — Connection from the client side

On SRV: 

# in pane 0 (to the left)
dd if=/dev/zero of=/tmp/big.bin bs=1M count=50

On CLIENT: 

# in pane 1 (top right)
curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin

# in pane 2 (bottom right)
curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin

On CLIENT, while the downloads are still in flight:

# in pane 0 (left)
ss -tan '( dport = :8080 )'

On SRV: 

# in pane 0 (left)
ss -tan '( sport = :8080 )'

What just happened

  • We created a 50M file and dropped it in the directory the web servers serve files from. The file is intentionally large to make the download slow and observe the connection in flight.
  • We use the --limit-rate option of curl to further slow down the download to a crawl
  • ss -tan — shows all TCP connections, filtered by destination port on CLIENT, and by source port on SRV. Compare them and notice how they mirror each other.
  • We never specified the clients' port numbers; so where are they coming from?

On CLIENT: 

sysctl net.ipv4.ip_local_port_range

  • On the client, the kernel allocates port numbers from a system-defined range of ephemeral ports. The ports are handed out temporarily for the life of a connection and returned afterwards.

  • So ports come in two kinds, depending on whether they need to be known in advance:

    • A server port is fixed and published, because clients must be able to guess it — 80, 443, 22, 53.
    • A client port is temporary and arbitrary, because only the two machines involved ever need to know it.

Do this — The 3-way handshake

First, start a capture on the SRV cable.

On CLIENT: 

curl -s -o /dev/null http://192.168.10.2:8080

In Wireshark, type tcp.port == 8080 in the filter box to show only packets involved in this connection.

Read the first 3 packets and fill out the following table:

What just happened

  • The handshake is three packets: SYN → SYN/ACK → ACK. They carry no data, and communicate through the flags each sets.
  • Each side chooses an initial sequence number and tells the other. Each side also acknowledges the other's. That is the entire ceremony.
  • Sequence numbers are used to count bytes, which is how the connection keeps tracks of what has been transmitted at any given point in time. Acknowlegement numbers keeps track of what has been received.
  • The connection is invisible from the network. It is entirely held in memory at the two ends of the conversation.

In Wireshark, type tcp.flags.fin == 1 in the filter box. Fill in the table below:
Flags on the closing packets
How many packets to close

What just happened

  • Another handshake closes the connection: FIN → ACK → FIN → ACK. Each direction is shut down separately, because a TCP connection is really two independent streams that happen to share a socket. One side can stop sending while still receiving.
  • The side that closes first moves into the TIME-WAIT state for a while. This ensures the socket is still ready to receive any delayed packets that may come from the opposite direction.
  • The side that receives the FIN moves into the CLOSE-WAIT state if not ready to end the connection yet (see connection states below).

Do this - Connection states

On SRV: 

modprobe sch_netem

tc qdisc add dev eth0 root netem delay 3s

This loads the network emulator kernel module used by tc (traffic control) — a linux traffic shaping tool.

We are imposing a delay of 3 seconds on every outgoing packet, to slow down responses from the server, giving us a better chance to see the different connection states.

On CLIENT: 

# in pane 0 (to the left)
watch -n0.2 'ss -tan state all "( dport = :8080 or sport = :8080 )"'

# in pane 1 (top right)
ncat 192.168.10.2 8080
GET / HTTP/1.1
Host: 192.168.10.2

# ensure the above empty line is entered by pressing ENTER twice

We are using ncat to slow things down by sending the request at human typing speed.

What just happened

  • ESTAB is the state after the 3-way handshake. Data is sent during this state.
  • SYN-SENT, SYN-RECV are temporaly states of the 3-way handshake
  • FIN-WAIT, TIME-WAIT are temporary states of the connection teardown.
  • These states are read from the kernel's socket table — a connection is just a slice of memory. It is invisible from the network.

Do this - clean up

On SRV: 

tc qdisc del dev eth0 root
