Flow Control

Time: 20 min

Needs: the topology from the previous activity

GNS3 project: w12-a1-transport (reuse it)

Info

Times listed are approximate and provided as timing guidelines only. Take as much time as you need to complete the activity.

Do this - set it up

On SRV: 

dd if=/dev/zero of=/tmp/big.bin bs=1M count=50

cd /tmp && python3 -m http.server 8080

Capture SRV's link, then on CLIENT:

curl -s -o /dev/null http://192.168.10.12:8080/big.bin

In the capture, find the SYN and look for the MSS option, then look at the size of the data packets that follow.

What just happened

  • The data file was cut into thousands of segments, each one small enough to fit in a frame — around 1460 bytes of data apiece. Compare this number to the value of the maximum segment size in the initial SYN packet.

Do this — Read slowly

Stop the existing capture and start a new one.

On CLIENT: 

curl --limit-rate 20k -o /dev/null http://192.168.10.12:8080/big.bin

Let it run for thirty seconds, then pause the capture. In Wireshark, look at the Win= value on packets from CLIENT, and watch for packets Wireshark colours and labels TCP ZeroWindow and TCP Window Update.

What just happened

  • The window field in every acknowledgement tells the sender how much data the receiver is prepared to accept. This values is dynamic, changing from one ACK to another.
  • curl was slow, which made CLIENT buffer fill up, resulting in the advertised window shrinking.
  • When the window reached zero, CLIENT sent a ZeroWindow, which means "stop, I have no space left in my buffer".
  • A Window Update was sent after CLIENT had read some more, indicating to SRV that it could resume sending.
  • Flow control is driven by the receiver. The transfer moves at the speed of the slowest participant. The network has nothing to do with any of this, apart from influencing the initial MSS
