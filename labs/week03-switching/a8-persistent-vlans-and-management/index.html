W3·A8 — Configuration that survives, and a switch you can log into ★

Time: 80 min · Needs: two OL9 Switches (SW1, SW2), two OL9 PCs (PC1, PC-MGMT), 1 VPCS · GNS3 project: w03-a8-persistent

The question: everything you have built this week disappears when the node restarts, and none of it can be administered from anywhere except the console. Both of those are unacceptable in a building you do not want to visit. Fix both.

This activity is milestone 1 in miniature — VLANs, a trunk, redundancy, a management network and persistence, on two switches instead of three. Nothing here is a new idea. What is new is writing it so it stays written.

Build it

Node Type Attaches to VLAN Address
SW1 OL9 Switch — — 192.168.10.201 in VLAN 99
SW2 OL9 Switch — — 192.168.10.202 in VLAN 99
PC1 OL9 SW1:eth0 10 192.168.10.11/24
PC2 VPCS SW2:eth0 10 192.168.10.12/24
PC-MGMT OL9 SW2:eth1 99 192.168.10.200/24

Two inter-switch links: SW1:eth2↔SW2:eth2 and SW1:eth3↔SW2:eth3. Yes, that is a loop — A5 taught you what to do about it, and this time it will be configured to stay done.

PC1 and PC-MGMT are OL9 rather than VPCS because both need to run ssh, which VPCS cannot.

Everything is in 192.168.10.0/24, management included. That is deliberate and it is the same arrangement milestone 1 uses: it makes the point that the switch defines the segment, not the addressing — VLAN 99 is a separate broadcast domain even though its addresses look like everyone else's.

Predict first

  1. You configure everything with ip and bridge as in A4 and A5, then restart the node. What is left?
  2. PC-MGMT is plugged into SW2. Can it administer SW1, which it has no cable to?
  3. Can PC1, in VLAN 10, log into a switch?
  4. SW1 is the root of the spanning tree. Does that make it the switch you manage?

Part 1 — The same bridge, written down

Running state, and stored configuration. Both kinds of command change the machine, so the difference is not that one is real and the other is pretend.

ip and bridge change the machine as it is running now. The change is in the kernel's memory, it takes effect the instant you press return, and it is gone when the node restarts. Nothing anywhere records that you wanted it.

nmcli con add writes a stored configuration — a statement of what this machine's networking should be. NetworkManager then keeps the running state matching it: at boot, when a cable is plugged in, and whenever else it decides to re-apply.

That second half matters beyond surviving a restart. If a card has stored configuration saying "ask the network for an address", and you set an address by hand, yours exists only in running state — and the stored one wins the moment NetworkManager acts on it. Nothing warns you. Any activity where something on the wire hands out addresses is an activity where the difference stops being academic.

On SW1, build the bridge — but this time as configuration on disk rather than as commands to a running kernel:

# on SW1
nmcli con add type bridge ifname br0 con-name br0 \
      bridge.vlan-filtering yes \
      bridge.vlan-default-pvid 0 \
      bridge.stp yes \
      bridge.priority 4096 \
      ipv4.method disabled ipv6.method disabled

Six settings, and each one is something you did by hand earlier in the week:

Setting The A4/A5 command it replaces
bridge.vlan-filtering yes ip link set dev br0 type bridge vlan_filtering 1
bridge.vlan-default-pvid 0 the mandatory for loop deleting vid 1 from every port
bridge.stp yes ip link set dev br0 type bridge stp_state 1
bridge.priority 4096 ip link set dev br0 type bridge priority 4096
ipv4.method disabled not putting an address on the bridge — A2's whole point

bridge.vlan-default-pvid 0 deserves a second look. In A4 you had to delete vid 1 from every port or nothing was separated, and the activity appeared not to work. That default is what put it there. Setting it to 0 means new ports get no automatic VLAN at all, so the only VLANs a port has are the ones you gave it — which is the behaviour you wanted in the first place.

Now the ports. An access port in VLAN 10, and the management port:

# on SW1
nmcli con add type bridge-slave ifname eth0 master br0 con-name p-eth0 \
      bridge-port.vlans "10 pvid untagged"

And the two trunks, tagged members of both VLANs:

# on SW1
nmcli con add type bridge-slave ifname eth2 master br0 con-name p-eth2 \
      bridge-port.vlans "10,99"
nmcli con add type bridge-slave ifname eth3 master br0 con-name p-eth3 \
      bridge-port.vlans "10,99"

nmcli con up br0
bridge vlan show

What just happened

  • bridge-port.vlans is the whole of A4 in one property. "10 pvid untagged" is an access port — frames arriving here belong to VLAN 10, and frames leaving here have the tag stripped. "10,99" with no pvid untagged is a trunk — a tagged member of both VLANs.
  • Compare bridge vlan show with what you got in A4. It is the same kernel state. NetworkManager is not a different mechanism; it is the same mechanism with a file behind it.
  • VLAN 99 is on the trunks. It has to be: PC-MGMT is attached to SW2 and has to reach SW1, and the only path between them is the trunk. A management VLAN that stops at each switch manages nothing.

Repeat all of it on SW2, with two changes — eth1 is an access port in VLAN 99 for PC-MGMT, and SW2 is not the root, so leave its priority alone:

# on SW2
nmcli con add type bridge ifname br0 con-name br0 \
      bridge.vlan-filtering yes bridge.vlan-default-pvid 0 bridge.stp yes \
      ipv4.method disabled ipv6.method disabled

nmcli con add type bridge-slave ifname eth0 master br0 con-name p-eth0 \
      bridge-port.vlans "10 pvid untagged"
nmcli con add type bridge-slave ifname eth1 master br0 con-name p-eth1 \
      bridge-port.vlans "99 pvid untagged"
nmcli con add type bridge-slave ifname eth2 master br0 con-name p-eth2 \
      bridge-port.vlans "10,99"
nmcli con add type bridge-slave ifname eth3 master br0 con-name p-eth3 \
      bridge-port.vlans "10,99"

nmcli con up br0
bridge link

PC1 and PC2 get their addresses as usual. Confirm PC1 can ping PC2 — VLAN 10 across the trunk — and check bridge link on both switches: one port blocking, no storm, exactly as A5 predicted.

Part 2 — Giving a switch an address

Your bridges have deliberately had no IP address all week. A2 explained why: a switch is not a host on the segment, it is the segment, and a port carrying an IP is a router leg rather than a bridge port.

So where does a management address go? Not on a port — that would put it in whichever VLAN the port belongs to and make it a host there. It goes on an interface attached to the bridge from the inside, inside one VLAN. The bridge is a switch with many VLANs; you are plugging a small management host into one of them, and that host happens to be the switch's own IP stack.

Two steps. First tell the bridge that it is itself a member of VLAN 99 — not a port, the bridge:

# on SW1 and SW2
nmcli con modify br0 bridge.vlans "99"
nmcli con up br0
bridge vlan show          # note the new line for br0 itself, not for any ethN

Then create the interface that lives in that VLAN and carries the address:

# on SW1
nmcli con add type vlan ifname br0.99 con-name mgmt dev br0 id 99 \
      ipv4.method manual ipv4.addresses 192.168.10.201/24 \
      ipv6.method disabled
nmcli con up mgmt

# on SW2 — same, with .202

On PC-MGMT, which is an ordinary host on an access port and therefore needs no tagging at all:

# on PC-MGMT
nmcli con add type ethernet ifname eth0 con-name mgmt0 \
      ipv4.method manual ipv4.addresses 192.168.10.200/24 ipv6.method disabled
nmcli con up mgmt0

ping -c2 192.168.10.202      # the switch it is plugged into
ping -c2 192.168.10.201      # the switch it is not

(Rendered version for slides or print: topologies/a8-management-path.svg.)

Each switch is drawn with its ports facing the other and its own IP stack facing away — because that is what a management interface is: an attachment to the bridge from the inside, not one of the ports. PC-MGMT is in VLAN 99 on SW2:eth1, and your two pings take quite different journeys.

.202, the switch it is plugged into. Untagged into eth1, so it takes that port's PVID and becomes a VLAN 99 frame. FDB lookup happens inside VLAN 99, the destination MAC is the bridge's own, so the result is not "out a port" but "deliver locally" — egress toward br0, which VLAN filtering checks like any other port. br0 is a member of 99 and the entry is tagged, so the frame arrives at br0.99 still carrying its header, and br0.99 pops it. The frame never leaves SW2.

.201, the switch it has no cable to. Identical until the FDB, which this time points out the forwarding trunk — tagged, because eth2 is a tagged member. SW1 classifies it on ingress by that tag, looks up VLAN 99, finds its own MAC, and hands it up its own br0 → br0.99. This is the concrete reason VLAN 99 has to be on the trunks: without it the frame is dropped by ingress filtering at SW1:eth2 and SW1 is unreachable, cable or no cable.

Both replies retrace the same steps in the other direction, br0.99 pushing the tag back on.

And PC1, in VLAN 10, gets as far as the FDB and no further: neither bridge has a vid 10 self entry, so there is no path from VLAN 10 to either IP stack. That is prediction 3, and the isolation is one line of VLAN membership enforced at one place.

What just happened

  • bridge vlan show now has a line for br0 itself. Every other line is a port — a way into the switch from outside. This one is the switch's own way in, from inside. That is the difference between a bridge port and a management interface, and it is the thing milestone 1 makes you work out.
  • PC-MGMT reached SW1, which it has no cable to, through SW2 and across a trunk. That is what makes this a management network rather than a management port.
  • SW1 and SW2 are still not hosts in VLAN 10, 20 or 30. They have exactly one address each, reachable from exactly one VLAN.

Part 3 — Actually managing something

A ping proves a switch is alive. It does not administer anything. From PC-MGMT:

ssh admin@192.168.10.201
bridge vlan show
exit

Now do it to the whole fleet from one chair, without logging into anything:

# on PC-MGMT
for s in 201 202; do
    echo "=== switch at .$s ==="
    ssh admin@192.168.10.$s 'bridge link'
done

And from PC1, in VLAN 10, try exactly the same thing:

# on PC1
ssh admin@192.168.10.201

What just happened

  • That is the answer to "why does a switch need an address." Not to be pinged — to be read, audited and changed from somewhere other than a chair in front of it. Two switches is already too many consoles to walk to; a building has forty.
  • The loop over .201 and .202 is a real operations task — collecting the state of every device to compare it against what you think you deployed. It is also how you find the one switch somebody changed by hand at 2am.
  • PC1 hung and failed, and the reason matters. Nothing blocked it. There is no firewall rule and no password involved — VLAN 10 and VLAN 99 are separate broadcast domains with no router between them, so the packet had nowhere to go. It is the same reason PC1 cannot reach a host in VLAN 20: not forbidden, unreachable.
  • Notice what that means for milestone 2. Once a router arrives and VLANs can reach each other, PC1 will be able to reach the switches, and keeping it out stops being a happy accident of topology and becomes a decision somebody has to make and configure.

Part 4 — Changing the network from somewhere else

SW1 is currently root, and PC-MGMT is plugged into SW2. Confirm both facts from PC-MGMT without touching a console:

# on PC-MGMT
for s in 201 202; do ssh admin@192.168.10.$s 'cat /sys/class/net/br0/bridge/root_id'; done

Both should print SW1's bridge ID. Now move the root to SW2 — from PC-MGMT, over the network:

# on PC-MGMT
ssh admin@192.168.10.202 'sudo ip link set dev br0 type bridge priority 2048'

Wait about 30 seconds, then re-run the loop above, and check bridge link on both.

What just happened

  • The root moved, and your management did not care. You reached both switches before, and you reach both switches now. The root is a spanning-tree decision about which way frames travel; the management address is a host interface in a VLAN. They have nothing to do with each other, and nothing about being root makes a switch more or less administrable.
  • Read that against the two states you have now seen: at the start the root was SW1, a switch PC-MGMT has no cable to. Now it is SW2, the switch PC-MGMT is plugged into. Neither arrangement is more correct, and neither changed how you administer anything.
  • The blocked port moved too. Re-run the reasoning from A5 §5 and check that the port now blocking is the one the rules say should block.
  • If your session stalled for a few seconds before returning — that is STP reconverging, and you watched a live outage from inside a management session. It is exactly what a topology change feels like from the chair.

You can cut yourself off this way. You have just changed, over the network, the thing that decides how the network forwards. A worse change — putting SW2:eth1 in the wrong VLAN, say — would strand PC-MGMT with no path to anything, and the only recovery is the GNS3 console. That is not a lab artefact. Being locked out of a device you are configuring is a standard hazard with a standard answer: keep console access, and do not change the thing you are reaching the device through.

Put the root back where you meant it, and this time persistently, so it is still true after a restart:

# on SW2, via ssh from PC-MGMT
sudo nmcli con modify br0 bridge.priority 32768
sudo nmcli con up br0

SW1 already carries bridge.priority 4096 from Part 1, so it takes the root back.

Part 5 — The only test that counts

Stop both switches from the GNS3 toolbar. Start them again. Wait for them to boot, touch nothing, and from PC-MGMT:

# on PC-MGMT
for s in 201 202; do
    echo "=== switch at .$s ==="
    ssh admin@192.168.10.$s 'bridge vlan show; bridge link; cat /sys/class/net/br0/bridge/root_id'
done

Then ping PC2 from PC1.

What just happened

  • Everything came back: the bridge, VLAN filtering, every port's VLAN membership, both trunks, STP, the chosen root, and the management address. You typed nothing after the reboot.
  • Do the same experiment mentally for A4 and A5, which built the identical network with ip and bridge. After that reboot there is no br0 at all. Those commands were never wrong — they are for exploring, and they let you undo a mistake by restarting the node. They simply do not persist, and were never meant to.
  • Milestone 1 will be restarted during marking. This part is the one that decides whether it still works when it is.
