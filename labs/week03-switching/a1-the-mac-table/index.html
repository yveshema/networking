W3·A1 — The MAC address table ★

Time: 45 min · Needs: one OL9 Switch (6 adapters) + 4 VPCS · GNS3 project: w03-a1-mac-table

The question: since week 2 you have been saying "the switch learned where PC2 is". Learned it where? Show the table.

Build it

One OL9 Switch named SW1, with PC1…PC4 (VPCS) on Ethernet0…3.

Set Adapters = 6 (right-click → Configure → Network). You only need four now, but A4 continues in this same project and adds a fifth port for the link between two switches. Spare adapters cost nothing, and adding them later means shutting the node down again.

# on SW1
for i in eth0 eth1 eth2 eth3; do nmcli device set $i managed no; done

ip link add name br0 type bridge
ip link set br0 up

for i in eth0 eth1 eth2 eth3; do
    ip addr flush dev $i
    ip link set $i master br0
    ip link set $i up
done

bridge link
ip -d link show br0

# PC1 / PC2 / PC3 / PC4
ip 192.168.10.11/24        # .12 / .13 / .14
save

Confirm PC1 pings all three. br0 has no IP address and must not have one — this node is the segment, not a host on it.

What ip -d link show br0 told you

Three fields to find now, because the rest of the week uses all three:

Field Meaning Default
ageing_time how long a learned entry survives, in centiseconds 30000 = 300 s
stp_state spanning tree on/off 0 = off
vlan_filtering VLAN support on/off 0 = off

Predict first

  1. Before any traffic, how many entries are in the table? _
  2. PC1 pings PC2. How many entries afterwards, and whose? _
  3. Which packet taught the switch where PC2 is — PC1's request or PC2's reply? _

Do this — collect the MACs first

show ip on each VPCS prints its MAC. You cannot read the table without these.

Do this — read the table

# on SW1 — the interesting rows only.
# 'permanent' and 'local' entries are the bridge's own port addresses, not learned ones.
bridge fdb show br br0 | grep -v permanent | grep -v local

# forget everything learned so far
for i in eth0 eth1 eth2 eth3; do bridge fdb flush dev $i master; done
bridge fdb show br br0 | grep -v permanent | grep -v local

The second listing is empty. Now, on PC1:

clear arp
ping 192.168.10.12

And immediately on SW1, re-run the bridge fdb show.

What just happened

  • Two entries, and only two: PC1's MAC on eth0, PC2's on eth1. Check them against your table above. PC3 and PC4 are absent — the switch has never heard from them and has no reason to care.
  • The rule, in one sentence: a bridge learns from the source address of frames that arrive, and forwards on the destination. Nothing announces itself; the switch overhears.
  • So PC2's entry came from PC2's reply, not from PC1's request. The request taught it only about PC1. Traffic in one direction teaches only one direction, which is a fact week 4 will make expensive.
  • This is the table you have been inferring since W2·A1, and it was inferable because it is completely determined by what the switch has heard.

Do this — watch it forget

Ageing is in centiseconds, unusually for iproute2. 30 seconds is 3000:

# on SW1
ip link set dev br0 type bridge ageing_time 3000
cat /sys/class/net/br0/bridge/ageing_time        # cross-check: 3000

Then from PC1: ping 192.168.10.12, and on SW1 run bridge fdb show br br0 once immediately, once after 15 seconds, once after 35.

Put it back afterwards: ip link set dev br0 type bridge ageing_time 30000.

What just happened

  • The dynamic entries vanished on their own. Nothing deleted them and nothing went wrong.
  • A MAC table is a cache, not a configuration. It is never right, only recently correct, and a switch that has been idle knows nothing. Compare the ARP cache from week 1 — same idea at a different layer, and both must expire for the network to tolerate change (W2·A3 showed you what happens when something moves).
  • The default 300 s is a compromise: too short and the switch floods constantly; too long and it keeps sending frames to a port where nothing lives any more.

Do this — move a host

With ageing back at 300 s, ping from PC4 so the switch learns it. Then stop PC4, re-cable it from Ethernet3 to a free port, start it, and — without sending any traffic from it — check the table. Then ping from PC4 and check again.

What just happened

  • The entry still named the old port, and would have until it aged out. A switch cannot detect a move; it can only be told, and the only way to tell it is to transmit.
  • One frame from PC4 corrected it instantly. Learning is not a periodic process — it happens on every arriving frame, always.

If it went wrong

Symptom Cause Fix
Pings fail once the bridge is built br_netfilter handing bridged frames to iptables sysctl -w net.bridge.bridge-nf-call-iptables=0
Interfaces regain addresses on their own NetworkManager nmcli device set ethN managed no on all four, then rebuild
bridge fdb show lists only permanent rows no traffic yet, or you filtered too hard ping first; drop the grep -v to see everything
Table never ages you set 3000 seconds, not centiseconds cat /sys/class/net/br0/bridge/ageing_time and compare
Only eth0 exists adapter count Configure → Network → Adapters = 6, restart the node
