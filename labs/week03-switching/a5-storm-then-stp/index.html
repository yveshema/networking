W3·A5 — Storm, then spanning tree ★

Time: 75 min · Needs: two OL9 Switches + 4 VPCS · GNS3 project: w03-a5-stp

The question: in W2·A5 you added a redundant cable and the network died. Redundancy is supposed to be good. Fix it.

This activity deliberately builds a broadcast storm. Nothing is damaged, but the topology becomes unusable while it runs and it will load your machine. Know how to stop the nodes from the toolbar before you start.

Build it

Two OL9 Switches, SW1 and SW2, built exactly as in A1 but with eth0–eth3 bridged on each. PC1 .11 and PC2 .12 on SW1; PC3 .13 and PC4 .14 on SW2.

Cable both inter-switch links now — SW1:eth3↔SW2:eth3 and SW1:eth2↔SW2:eth2 — but hold the second one administratively down so that only one is live:

# on SW1
ip link set eth2 down
bridge link

Confirm all four PCs ping each other. That is your working baseline. You will cable nothing else for the rest of this activity; every "cable" you pull or restore from here is an ip link set command, which is faster and cannot leave a stale link in the project.

Predict first

  1. SW1:eth3 fails. What reaches PC3 from PC1?
  2. You bring eth2 up so that both links are live at once. What happens to PC1 → PC3?
  3. Where, exactly, does a looping frame stop?
  4. If you turn on a protocol that switches one of the two links off, how is that redundancy?

Part 1 — Why anyone runs a second cable

Right now the two switches are joined by exactly one working link. Everything on the far side of it depends on that one cable, that one pair of connectors, and nobody catching it with a chair leg.

Break it, with a continuous ping running from PC1 to PC3:

# on SW1
ip link set eth3 down

The ping stops. Not slows — stops. PC3 and PC4 are still powered, still configured, still perfectly healthy, and completely unreachable. Nothing on any host indicates what is wrong or where.

Now bring the spare into service by hand:

# on SW1
ip link set eth2 up

What just happened

  • The spare path worked. Traffic resumed over a different cable, and nothing on any PC was reconfigured to make that happen — the switches simply had another way across.
  • A human did it. Someone had to notice the outage, work out which link had failed, know that a spare existed, and type a command. Count the time that took you, and remember that you already knew the answer and were sitting in front of the right machine.
  • That is the case for redundancy, and it is why the second cable is bought: the alternative to a spare path is a site outage that lasts until a person physically finds the fault.
  • It is also the case for automating this. Everything after here exists to remove the human from the paragraph above.

Leave eth2 up and bring eth3 back:

# on SW1
ip link set eth3 up

Part 2 — So just leave both cables up

Which is the obvious idea. Both links are now live and you have just done it.

Check the counters first, so you have a "before":

# on SW1
ip -s link show eth3

Start a capture on the SW1↔SW2 link — right-click the link → Start capture — and from PC1:

ping 192.168.10.13

Watch for two seconds, then stop the capture. It grows at a rate you have not seen before and will fill a disk if you leave it. Then on SW1:

ip -s link show eth3
ip -s link show eth2

Then take the second link back down immediately: ip link set eth2 down on SW1.

What just happened

  • Read the capture. It is thousands of copies of one frame — the same ARP request, the same source MAC, the same target, arriving microseconds apart. PC1 sent that request once.
  • That is the observation that proves this is a loop and not merely a busy network. Nobody is generating this traffic. One frame is being copied.
  • The packet counters went from hundreds to enormous, climbing while you watched, on a network with four idle hosts on it.
  • SW1 flooded PC1's broadcast to SW2 over both links; SW2 flooded each copy back over the other; and so on, doubling, with nothing anywhere to stop it.

Why it never stops

Two mailing lists, each subscribed to the other. Someone posts one message. List A forwards it to list B, which forwards it back to list A, which forwards it on again. Neither list is broken and neither is doing anything other than its one job — faithfully passing on what it receives. Nothing in the message records how many times it has been forwarded, so nothing can ever decide it has been around enough times and drop it.

  • There is no hop count in an Ethernet frame. Week 1's teardown showed you exactly where TTL lives — in the IP header, one layer up. A frame circulating at layer 2 is never examined by anything that could count its hops, because at layer 2 nothing is counting.
  • Worse than the traffic: the MAC tables are being corrupted. Each switch sees PC1's address arriving on both ports, alternately, and rewrites the entry each time. Even frames that are not looping now go to the wrong port. This is why a storm takes out unicast traffic too, and why the network does not merely slow down — it stops.

So you are holding a contradiction. The second cable is the thing you must have for the network to survive a failure, and it is the thing that destroys the network the moment you use it.

How spanning tree resolves that

Read this before Part 3. It is the whole point of the activity.

1. Keep the cable, and refuse to use it

You already know the fix, because you did it by hand in Part 1: hold the spare down. The frames only loop because there are two live paths; with one path there is no circle.

The difference is that you are going to have the switch refuse to forward on that port, rather than shut the port off. The cable stays connected, powered, and listening. It carries no user traffic and it is ready instantly. A port in that state is called blocking.

2. The hard part is agreeing which port

Now the real problem appears, and it is not the one you would guess. The switches have to agree on which port blocks. If each decides on its own:

  • both might block, and the network splits into two halves that cannot reach each other;
  • or neither blocks, and the storm continues.

And there is no controller. No switch is in charge of the others, none of them was told what the topology is, and each can only see its own ports. So the question spanning tree actually answers is:

How do independent devices, with no coordinator, all reach the same decision?

3. Agree on a landmark first

You cannot answer "which of my ports should block?" by looking only at yourself — it depends on what everyone else does.

But it becomes easy the moment every switch agrees on one reference point somewhere on the network. Then each switch asks itself the same purely local question: which of my ports is on my best way to that point? Keep that one. Everything else can block. Nobody has to negotiate with anybody, and yet the answers fit together.

So before anything else, the switches choose one of themselves to be that reference point — the root. Each announces itself with a number, the lowest number wins, and because every switch hears the same numbers, every switch works out the same winner without being told.

That number is the bridge ID, and it is two things joined together:
priority a number you set — the part you control
MAC address the switch's own address — the part you cannot

Priority is compared first. The MAC is only consulted when priorities are equal, which is why it is a tiebreak and not the rule. Two switches, both left at the default:

SW1 SW2
priority 32768 32768
MAC 0c:1a:…:5e 0c:1a:…:3f
bridge ID 32768.0c1a…5e 32768.0c1a…3f ← root, its MAC is lower

Now set SW1's priority to 4096:

SW1 SW2
priority 4096 32768
MAC 0c:1a:…:5e 0c:1a:…:3f
bridge ID 4096.0c1a…5e ← root 32768.0c1a…3f

SW1 wins now, and SW2's lower MAC never gets looked at, because the comparison was already decided at the first field. Lower wins, at every step. The default is 32768, the range is 0–65535, and real switches accept it only in steps of 4096.

You will read your own values with cat /sys/class/net/br0/bridge/bridge_id.

4. "Best way" has to be measured

If a switch has two ways to reach the root, which is better? Add up the links along each route. Each link contributes a number based on its speed, and a faster link contributes less, because you would rather your traffic took the fast route:

Link speed Contributes
1 Gb/s 4
100 Mb/s 19
10 Mb/s 100

Add them along a path and you have that path's cost. Lower total is better. Say that to yourself once, because it runs against the instinct that a bigger number means a better link. bridge link prints the real cost of each of your ports — read it there rather than assuming.

Cost is a distance to the root. It cannot be computed until a root exists, which is why the root is elected first and why every decision below is described as being relative to it.

5. Now the three port roles are just three questions

"Which one of my ports do I use to reach the root?" — the root port. The port with the lowest cost to the root. Exactly one per switch, and the root itself has none, because it is already there.

"This cable has a switch on each end — which of the two is responsible for carrying it?" — the designated port. One per cable: whichever end has the lower cost to the root. This role exists because if both ends forwarded the same cable's traffic, that is the loop. Every port on the root is designated, since nothing beats a cost of zero.

"What is left over?" — blocking. Not a root port, not a designated port, so it forwards nothing. That is where the circle gets broken.

Worked through on a triangle, which is also the shape you will build for milestone 1. SW1 is root at priority 4096, all links gigabit, so each contributes 4:

Switch Bridge ID Cost to root
SW1 4096.aa…01 0 — it is the root
SW2 32768.aa…02 4 direct, or 8 via SW3 → 4
SW3 32768.aa…03 4 direct, or 8 via SW2 → 4
Cable SW1 end SW2 end SW3 end Outcome
SW1–SW2 cost 0 cost 4 — SW1's port designated; SW2's is its root port
SW1–SW3 cost 0 — cost 4 SW1's port designated; SW3's is its root port
SW2–SW3 — cost 4 cost 4 tie — see below

Six ports, and every one has a role: SW1 two designated, SW2 one root and one designated, SW3 one root and one blocking. Exactly one port blocks, which is exactly one more than the number of loops you had.

6. What happens on a tie

The SW2–SW3 cable has cost 4 at both ends. Neither is closer to the root, so cost cannot decide it, and something has to.

The rule is: lowest cost, then lowest bridge ID, then lowest port number. Here bridge ID settles it — …02 beats …03, so SW2's port is designated and SW3's blocks.

That tiebreak looks arbitrary because it is arbitrary, deliberately. A tiebreak does not have to be fair or meaningful. It has to be identical everywhere, so that every switch applying it alone arrives at the answer every other switch arrived at. Bridge IDs and port numbers are used for no better reason than that they are unambiguous and everybody already knows them.

This matters for what you are about to build. Your two switches have two links of the same speed between the same pair of bridges — so the costs tie and the bridge IDs tie, and the decision falls all the way through to port number. You can predict which port will block before you turn STP on.

Part 3 — Turn it on

With eth2 still down, enable STP on both bridges:

# on SW1 and on SW2
ip link set dev br0 type bridge stp_state 1

bridge link
cat /sys/class/net/br0/bridge/bridge_id
cat /sys/class/net/br0/bridge/root_id

Which switch is root, and did the MAC tiebreak decide it? Now bring the second link up and wait about 30 seconds:

# on SW1
ip link set eth2 up

# then, on both
bridge link

What just happened

  • One of the four inter-switch ports settled into blocking while the rest reached forwarding. The cable is physically connected, electrically fine, and carrying no user traffic at all. No storm.
  • Check it against your prediction: the blocking port is on the non-root switch, and which of its two ports it is was decided by port number, because everything above that tied.
  • bridge_id and root_id: where they are equal, that bridge is the root. Both switches agree on one root with nothing coordinating them, exactly as in §3 — they compared IDs, and the lowest won.
  • The delay was real. Classic 802.1D holds a port in listening then learning for 15 seconds each before forwarding. That 30-second silence is why a PC plugged into an unconfigured switch port can fail to get an address, and it is the reason RSTP exists.

Part 4 — Make it earn its keep

First, move the root deliberately rather than accepting whichever MAC happened to be lower:

# on SW1 — take over as root
ip link set dev br0 type bridge priority 4096
cat /sys/class/net/br0/bridge/root_id        # on both switches

Now repeat Part 1 exactly — with a continuous ping running from PC1 to PC3, fail the forwarding inter-switch link:

# on SW1
ip link set eth3 down

Watch the ping. Then bridge link on both switches.

What just happened

  • This is Part 1 with the human removed. The blocked port took over on its own. Nobody noticed the outage, diagnosed it, or typed anything — which is the answer to the fourth prediction. STP does not take your second cable away; it keeps it switched off and ready, and switches it on for you.
  • The ping stopped for a while and then resumed. Count the lost packets: classic STP takes tens of seconds to reconverge, and that is a genuine outage — shorter than the one in Part 1 by however long it would have taken a person to get there.
  • Lowering priority moved the root by decision. Left alone, the root is whichever bridge has the lowest MAC address — which is to say, an arbitrary device chosen by accident of manufacture, quite possibly the oldest and slowest thing you own, sitting in a cupboard. Every real deployment sets this explicitly, and now you know what goes wrong if nobody does.

Bring the link back up: ip link set eth3 up.

Note: Linux implements classic 802.1D, not Cisco's PVST+. Timings and behaviour match the standard rather than Packet Tracer's output. If you compare the two platforms, expect that difference and do not treat either as wrong.

This setting does not survive a reboot. ip link set ... priority is for exploring. Milestone 1 requires a deliberately chosen root that is still chosen after a restart, which is nmcli's job — see A8.

If it went wrong

Symptom Cause Fix
GNS3 unresponsive during Part 2 the storm is doing its job stop the nodes from the toolbar, then ip link set eth2 down
Capture file is enormous you left it running two seconds is plenty; stop it before reading
No storm at all second link not up at both ends, or STP left on from a previous run bridge link; stp_state must be 0 for Part 2
Both ports forwarding, no blocking STP enabled on only one bridge it must be on both
Ping never recovers in Part 4 still converging classic STP takes ~30 s; wait before concluding
Root keeps changing you set priority on both set it on one only
A different port blocked than you predicted port numbering, or the costs did not tie bridge link prints each port's cost — check them before blaming the prediction
Pings fail after the storm tables scrambled bridge fdb flush dev ethN master on each port, or restart both bridges
