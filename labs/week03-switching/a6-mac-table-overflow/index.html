W3·A6 — Filling the table (extension)

Time: 30 min · Needs: the Open vSwitch appliance + Docker on the GNS3 server (../../gns3-lab0-switching.md §D0) + 3 OL9 PCs or VPCS · GNS3 project: w03-a6-overflow

The question: A2 ended with a claim — that a switch whose table is permanently full behaves like a hub, and that this is an attack. Test it.

Why a third switch appears here. Every tool in this course has a ceiling, and this activity is the first place we hit one. The GNS3 Ethernet switch shows you nothing at all; the Linux bridge shows you everything it has, but it does not have this. To overflow a forwarding table in a classroom you must first make it small, and OVS exposes that as a setting (other-config:mac-table-size) while the Linux bridge on OL9's kernel does not — its per-port learning limit, fdb_max_learned, arrived in kernel 6.2 and OL9 ships older.

So Open vSwitch is not a better switch that you should have been using all along, and nothing later in the course switches over to it. It is an instrument, brought out for one measurement — the same way you reach for Wireshark rather than replacing ping with it. You will meet it once more, in the security material, for port mirroring, which the Linux bridge also cannot do.

Build it

Import the OVS appliance (§D0), place it as SW1, and cable PC1 .11, PC2 .12, PC3 .13 to its first three ports.

# on SW1
ovs-vsctl show

If it is empty:

ovs-vsctl add-br br0
for i in eth0 eth1 eth2; do ovs-vsctl add-port br0 $i; ip link set $i up; done
ovs-vsctl show

Confirm the hosts ping each other, then:

ovs-appctl fdb/show br0

What just happened

  • The same table as A1, from a different management layer — port, VLAN, MAC, and an explicit age in seconds, which neither the built-in switch nor the Linux bridge gives you. You can watch entries count up in real time.

Predict first

  1. A switch's forwarding table is full and a frame arrives for an address not in it. What happens?
  2. Roughly how many entries does a real access switch hold? _
  3. Why would an attacker want the table full?

Do this — shrink the table, then fill it

# on SW1
ovs-vsctl set bridge br0 other-config:mac-table-size=4
ovs-appctl fdb/flush br0
ovs-appctl fdb/show br0

Start a capture on PC3's link. Establish normal behaviour first: from PC1, ping -c1 PC2, twice. PC3's cable should be quiet on the second attempt, exactly as in W2·A1.

Now generate traffic from many different source addresses. On PC1 (must be OL9):

for i in $(seq 1 20); do
    mac=$(printf '02:00:00:00:00:%02x' $i)
    ip link add link eth0 name fake$i address $mac type macvlan
    ip link set fake$i up
    ip addr add 192.168.10.$((100+i))/24 dev fake$i
    ping -c1 -W1 -I fake$i 192.168.10.12 >/dev/null 2>&1
done

ovs-appctl fdb/show br0        # run this on SW1

Then, from PC1's real interface, ping PC2 again — and read PC3's capture.

What just happened

  • Twenty different source MACs arrived on one port, and the switch learned every one of them, because that is all learning is. It has no way to know they are fictitious.
  • The table hit its limit and started evicting real entries to make room. PC2's entry was among the casualties.
  • So PC1's next ordinary ping to PC2 was flooded — and PC3's cable carried it, exactly as in A2, but now permanently rather than for one frame, because the fake addresses keep the table full.
  • A switch under this attack is a hub. Every port can read every conversation, and nothing on any host indicates that anything is wrong. Connectivity is perfect. That is what makes it useful to an attacker and hard for a user to notice.

Clean up

# on PC1
for i in $(seq 1 20); do ip link del fake$i; done

# on SW1
ovs-vsctl remove bridge br0 other-config mac-table-size
ovs-appctl fdb/flush br0

What defends against this

Not part of the build — read and answer.

  • Real switches implement port security: a limit on how many MAC addresses one port may learn, and an action when it is exceeded (drop, alarm, shut the port).
  • Note where the limit sits: per port, not per switch. A legitimate port has one or two hosts behind it; twenty is already implausible. The defence works because the attack has to be loud on one port.
  • Note also what is not a defence: encryption protects the contents but not the fact of the conversation, and VLANs limit the blast radius without stopping it inside a VLAN.

What the switch did wrong

One sentence: the switch behaved exactly as designed. So what is the actual flaw?

If it went wrong

Symptom Cause Fix
Docker errors on placing the appliance no Docker on the GNS3 server §D0 — the GNS3 VM has it; a bare Linux server needs it installed
mac-table-size has no effect typo in other-config ovs-vsctl list bridge br0 and check the field
macvlan creation fails not root, or name collision run as root; clean up leftovers with ip link del fake$i
Table never overflows pings failed, so no frames were sent drop the >/dev/null and check they are transmitting
Flooding stops on its own fake entries aged out re-run the loop, or lower mac-aging-time
