W3·A2 — Flooding what it does not know

Time: 35 min · Needs: A1's topology, with PC1 replaced by an OL9 PC · GNS3 project: w03-a1-mac-table (continue in it)

The question: in week 2 a bystander's cable carried a broadcast. This is a switch flooding an ordinary unicast frame — one addressed to a specific machine that is not the bystander. Easy to confuse with broadcast flooding, and worth separating properly.

Adjust the topology

PC1 must become an OL9 PC for this activity, because VPCS cannot pin a static ARP entry. Delete the VPCS PC1, drop in an OL9 PC in its place on Ethernet0, and:

# on the new PC1
nmcli device set eth0 managed no
ip addr add 192.168.10.11/24 dev eth0
ip link set eth0 up
ping -c1 192.168.10.12

Note PC1's new MAC — the table you filled in during A1 is now out of date for this row.

Predict first

PC1 sends a frame addressed to PC2's MAC. The switch has no entry for that MAC.

  1. Does the switch drop it? ☐ drop ☐ flood ☐ hold it and ask
  2. Does PC3's cable carry it? ☐ yes ☐ no
  3. Is this frame a broadcast? ☐ yes ☐ no

Do this — remove both reasons to broadcast

Two things normally prevent this experiment: PC1 would ARP (a broadcast, which muddies the result), and the switch would already know PC2. Remove both.

# on PC1 — pin PC2's MAC, so no ARP is needed
ip neigh replace 192.168.10.12 lladdr <PC2-MAC> dev eth0 nud permanent
ip neigh show

# on SW1 — forget PC2, and only PC2
bridge fdb del <PC2-MAC> dev eth1 master
bridge fdb show br br0 | grep -v permanent | grep -v local

Start a capture on the PC3↔SW1 link. Then on PC1:

ping -c1 192.168.10.12

Read the capture. Then run the ping a second time and read it again.

What just happened

  • PC3's cable carried the echo request — and it is not a broadcast. Look at the destination MAC in the capture: it is PC2's real address, not ff:ff:ff:ff:ff:ff. PC3 received a frame addressed to somebody else.
  • The switch did that on purpose. Faced with a destination it could not place, it did the only thing that preserves connectivity: send it everywhere except where it came from, and let the wrong recipients discard it.
  • PC3's NIC dropped it silently, because the destination MAC was not its own. The frame arrived, was examined, and was discarded — no error, no log, nothing. That filtering is done by the receiving card, not by the network.
  • The second ping put nothing on PC3's cable. PC2's reply taught the switch where PC2 is, so the flooding stopped after exactly one frame.

The distinction, stated

Broadcast flooding (W2·A1) Unknown-unicast flooding (here)
Destination MAC ff:ff:ff:ff:ff:ff a real host's address
Why it floods the address means "everyone" the switch cannot place the address
Stops when never — always floods the switch learns that MAC
Who processes it every host one host; the rest discard

Flooding is not a property of broadcast frames. It is what a switch does with any destination it cannot place, and week 2's example happened to be a broadcast.

Do this — the security consequence

Leave the static ARP entry in place. On SW1, flush PC2 again, and this time capture on PC3's link and PC4's link simultaneously before pinging.

What just happened

  • Every port got the frame. For as long as a switch does not know where a host is, traffic for that host is delivered to everyone — a hub, temporarily, for one destination.
  • Now consider forcing that state to persist. If the table could be kept permanently full of useless entries, the switch would flood everything, permanently, and any port could read any conversation. That attack is real, it is called MAC flooding or CAM table overflow, and A6 performs it.

Clean up

# on PC1
ip neigh del 192.168.10.12 dev eth0

Record
Destination MAC of the flooded frame
Was it a broadcast?
Did PC3's cable carry it? 1st ping / 2nd ping
What stopped the flooding
Who discarded the frame at PC3

One sentence distinguishing broadcast flooding from unknown-unicast flooding.

If it went wrong

Symptom Cause Fix
ARP frames still appear static entry not applied ip neigh show — the line must read PERMANENT
bridge fdb del says "No such file or directory" wrong port, or already flushed bridge fdb show first and copy the exact dev
Nothing on PC3's link at all the switch had already re-learned PC2 flush again, then ping immediately
Flooding never stops PC2 is not replying ping PC2 from the switch's own console? No — check PC2 is started and addressed
VPCS PC1 will not take the ip neigh command it is not Linux PC1 must be an OL9 PC for this activity
